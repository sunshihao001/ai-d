# 项目多层锚点与跨层一致性｜从认知约束到可核查工程关系（候选 V0.3）

日期：2026-11-13｜状态：已核对现有ai-d与Blix源码的知识/方法候选；**没有建立通用自动锚点系统，也没有独立实验验证有效性**。

## 0. 准确理解“锚点”

用户提出的不仅是“目标不要变”，而是：**在知识研究、来源采集、专业解释、设计决策、代码实现、测试验收和长期运行中，存在多种性质不同但相互关联的锚点；项目发生变化时，能保持必要约束、发现上游与下游受影响内容，并知道何时应修订或撤销。**

一个有用的锚点应能回答四个不同问题：
1. 为什么存在：它关联哪个人类目标/专业事实/重要失败经验？
2. 约束什么：哪个判断、输入、程序行为或实施选择必须受它影响？
3. 怎样检查：有何来源、条件、反例、测试或运行观测能证实它被执行？
4. 何时失效：出现哪种新事实、目标变更或反例后要重审，影响范围在哪？

**并非所有锚点都是永久不变的命令。** 有的是用户确认的价值边界，有的是可修正设计决策，有的是协议事实，有的是风险告警阈值，还有的是尚未验证的机制假说。只有事实和权限允许，才能转化为代码层的强制断言。

## 1. 三个层面先分清楚

- **项目要做成什么**：目标/业务/用户场景。Blix中的市场机会、关键钱包、库存和跨Mint属于这一层。
- **知识怎样形成与提升可靠性**：ai-d的K1–K9，P1–P8及跨学科证据研究。九阶段是生命周期视角，而不是九个必须运行的Agent。
- **一个重要认识怎样影响工程**：本文的跨层锚点。它是贯穿目标、来源、知识、代码、测试与运行的关系，不是重新定义专业本体或多增一个实施阶段。

## 2. 锚点对象按作用分类：不是八种互不相关的固定实体

| 作用位置 | 想保持或检验的东西 | 典型载体 | 不应误判 |
|---|---|---|---|
| 目标 G | 用户确认的价值方向、重大边界、允许改变的条件 | 目标入口/已批准的决策 | AI的最新建议不自动变更用户的真实目标 |
| 业务 B | 可完成的用户任务、所需输入与实际输出 | 场景验收、业务文档 | “按钮已存在”不等于任务完成 |
| 知识 K | 定义、机制、方法、适用与反例 | 原知识文件的具体主张 | 作者主张/模型猜测不等于链上事实 |
| 数据 D | 来源、口径、时间、样本、覆盖、精度和缺口 | 数据契约、存档、查询输出 | 浏览器观察时间不等于首次可交易时刻 |
| 设计 A | 多方案取舍、复用原因、依赖和许可 | 既有设计文档或必要时ADR | 可撤销的设计选择不是永久的用户指令 |
| 代码 C | 可检查的业务不变量、权限限制、边界处理 | 关键实现、接口、断言 | 注释不是机器强制执行；需看实际运行路径 |
| 验收 T | 正例、反例、性能/安全/恢复、主张的证据等级 | 自动测试、真实案例、实验收据 | 合成测试通过不等于真链/生产验证 |
| 运行 R | 事件、源中断、失效阈值、恢复及结论修订 | 监控、Case/事件、台账 | 设计了触发器不等于已持续运行 |

每个锚点还要有**性质**：
- **稳定性**：稳定目标、协议/事实、暂定方案、临时假说、数据质量阈值、告警触发。
- **效力**：说明性参考、实施时应检查的条件、可执行校验、明确权限/安全禁止。
- **证据等级**：原始来源/作者声明、静态源码、离线反例、真实运行、样本外增益与UNKNOWN，分别归属到某项具体主张。
- **生效条件**：适用对象、时间窗、版本和授权边界；只有条件匹配才施加约束。

例如“初期AI只读，不向交易程序授予签名能力”是当前明确的安全边界；“优先复用原数据管道”是可经性能/覆盖实测调整的工程选择；“两个地址是同控”通常仅是待证实假说，不能转为强制规则。

## 3. 一个锚点怎样关联另一个锚点：关系必须有可区分语义

| 关系 | 含义与实际判断 |
|---|---|
| derives_from（来源于） | 主张从哪份原始证据、哪个用户目标产生；引用不自动证明真实性 |
| supports / contradicts（支持/反证） | 具体证据支持或反驳具体主张；需说明适用范围，支持不是因果证明 |
| requires（依赖） | 后续结论或功能依赖什么源/权限/覆盖/计算；依赖缺失应降级或中止 |
| constrains（约束） | 数据或知识边界要求代码/决策不能作出什么错误声明 |
| implements（实现） | 哪个明确函数/接口落实设计或业务要求；需要源码或测试核实 |
| verified_by（被什么检验） | 某条可观测行为经哪项离线/真实/前瞻测试验证；不得混写等级 |
| impacts（变更影响） | 上游改变后需要复查的直接下游，不意味着所有关联文件都应重写 |
| supersedes（取代） | 新知识/决策替代旧主张，保留历史版本与理由，不暗删反例 |
| triggers_review（触发复查） | 新错误/时效失效/数据断流/版本变更时谁需要重新评估 |
| contextualizes（仅解释背景） | 相关知识可辅助模型推理，但不提供额外链上证据或权限 |

这些语义复用原有ai-d知识维护规范的PROV/SKOS思路；新增的是**跨知识—业务—代码—测试的实际可核影响关系**，不是为每类关系新建数据库。

## 4. 最小记录方式：一条重要锚点最多保留这些信息

不要求每个函数都注入元数据；优先在现有知识文档、业务总图、决策、测试中用短小可回查的文字记录：

| 字段 | 例子与理由 |
|---|---|
| Anchor ID / 主维护处 | 稳定ID + 知识/业务/设计里唯一权威链接，便于被多个代码点引用 |
| 主张与性质 | “观察到后卖出≠卖出刚转入的同批Token”，属于专业推论边界 |
| 来源与证据状态 | 原协议/经济证据、哪次存档或测试已支持、哪些仍未实测 |
| 生效条件及例外 | 只在单Mint已捕获交易的局部窗口，不能推成完整钱包历史 |
| 直接影响和验证 | 映射到实际函数、报告字段、已有自动测试及当前能力限制 |
| 触发修订的条件 | 新增完整库存批次、原始交易证据或反例后重算 |
| 状态/用户权限 | 已接受的安全边界、候选假说、局部测试、UNKNOWN等分开 |

**可按需使用**；一条重要项目安全限制可能需要全部字段，一项一般术语概念可能只需来源与适用范围。ID要稳定，重命名文件后保留引用；历史锚点不因为代码搬移就丢失理由。

## 5. 跨层变更影响：先查直接相关的边，不做全文件复制和全系统重规划

**正向：目标或知识发生变化**
1. 判断改变的是用户目标、专业事实、来源可用性、设计取舍，还是未经验证的猜测；
2. 沿已记录的requires/constrains/implements/verified_by查出**直接受影响**的接口、指标、策略及测试；
3. 区分必须修、需要人工/AI复核、不受影响三个结果，并说明来源与理由；
4. 采用局部代码修正与专门反例测试；若影响业务闭环再扩大检查范围；
5. 真实验收后回填状态；若无法完成，公开UNKNOWN和停止条件。

**反向：代码或测试发生变化**
1. 检查修改的函数是否已有重要业务不变量/权限约束及对应知识来源；
2. 既有测试是否仍代表原业务意义，还是只锁住了旧代码输出；
3. 原始数据字段、时间和覆盖语义变化是否会破坏下游AI结论/界面；
4. 失败记录关联哪个上游假设，区分代码bug、知识误读、来源中断及用户目标改变；
5. 若是新的实证机制，再修原知识记录；不能从一次测试失败直接推翻全部目标。

**防止误用**：影响关系应有可验证路径。不能因为两个文件都讨论“钱包”，就认定两者存在强制技术依赖。未知关系可以标为“可能受影响，待核”，不制造伪精准图谱。

## 6. 具体反例：Solana 钱包转入与后续卖出

原专业主张：观察到A转给B Token且B后卖出，仅证明**事件先后和本地摘要**，不能凭空证明卖出的是A转入的那批库存。

映射方式：
- 目标 G：提高链上真实资金调查与交易机会判断的准确性；
- 业务 B：单Mint调查必须区分“转入后观察到卖出”和“库存归属已证明”；
- 知识 K：Token账户/Owner和库存成本的具体机制、共享公共服务的反例；
- 数据 D：原始签名/指令身份、Mint、Owner/资产净额、历史覆盖和不可见缺口；
- 设计 A：先复用现有捕获RPC的只读证据；不擅自推成本基础；
- 代码 C：已有Blix经济证据映射可输出本地卖出摘要，但不能确认库存批次；
- 验收 T：已有离线经济关系与claim trace测试只验证局部来源分离；需要额外真实签名/净资产反例测试；
- 运行 R：真实新证据改变库存认定才触发重审；当前尚未建立完整自动监控。

如果未来新代码把“本地卖出摘要”改成“转入筹码已卖出”，这个变更应自动或人工触发库存归因锚点复核、补反例和业务报告审查；测试绿灯不足以自动许可强推论。

## 7. 外部成熟知识的借鉴、边界和工程选型

- NASA Requirements Management强调从利益相关者需求到设计与验证的**双向追溯**，以及检测没有上游依据的“镀金功能”。https://www.nasa.gov/reference/6-2-requirements-management/ 。借鉴“往上找目标、往下找验收”，不是照搬航天认证负担。
- W3C PROV-O区分实体、生成活动、归属和衍生，用来澄清“数据原文 → 计算 → 主张”的来源链。https://www.w3.org/TR/prov-o/ 。借鉴语义，不先部署RDF本体系统。
- Architecture Decision Record记录有重大后果的设计决定及其背景、备选和后果。https://martinfowler.com/bliki/ArchitectureDecisionRecord.html 。适用于重要转向，不必给每个函数写ADR。
- OpenTelemetry稳定性规范说明观测语义的改变可能破坏下游工具/面板。https://opentelemetry.io/docs/specs/otel/versioning-and-stability/ 。借鉴“字段含义发生改变须检查消费者”，不意味着现有Blix引入OpenTelemetry。

成熟资料提供可复用的**部分机制**，并没有证实这里的组合方案已经产生更高研发正确率。是否需要自动化图谱、静态分析或CI锚点扫描，必须先用真实项目检验人工轻量映射有没有减少遗漏，再比较成本决定。

## 8. 锚点失效与自我修订条件

- 有证据的新业务需求改变长期目标 → 由用户决定是否修改目标锚点，AI指出受影响业务；
- 新协议/原始链上反例否定专业判断 → 修改知识主张并回查所有受影响代码/测试；
- 库存数据不可用 → 降低结论等级或阻止本次主张，不能把未知填零；
- 被测试的代码只符合形式不符合用户真正业务 → 修业务验收，不用“测试通过”覆盖失败；
- 旧锚点与真实证据冲突 → 明确“保留历史/取代/暂不成立”，留下原因；
- 连续数轮只是给旧观点加新ID/文档，没有实际变更依据 → 停止锚点扩张，回到最早实证断点。

**四种最终状态必须清楚：文档锚定、代码条件已实现、自动测试已验证、真实运行已验证。** 对不同层次不得偷换“完成”的含义。

## 9. 与现有仓库的接入位置

- ai-d：本文件为跨领域方法的**单一主要维护位置**；从知识总索引和九阶段文档引用。P1–P8索引、organization-protocol、ACTIVE-RESEARCH-LEDGER原位保留。
- Blix：在原有V2总蓝图、专业知识入口、build-register内部链接一份具体项目“关键锚点映射与变更影响示范”；映射到现成真实函数和测试，**不建独立锚点引擎或第二套业务目标/数据仓库**。
- 未来其他领域：按需求借鉴“目标→关键主张→使用位置→验证→变更影响”这一最小片段，不能直接继承Solana资金机制或Blix账户/交易限制。

## 10. 下一项值得验证的成果

选择一个真变更场景，例如“Pulse浏览器时间被误用为真实首次可见”或“经济claim trace输出中的本地后卖出被误当已确认库存来源”，分别比较：
A. 只检查变更文件的局部测试；
B. 从知识/数据/业务锚点双向回查受影响调用方、说明和负例。

记录是否发现真正新漏项、错误减少、审查耗时/误报增加多少，以及哪些关系本身错误。**只有B在真实任务上的实际改进，才支持继续建设自动化锚点工具。** 不为了锚点数量而建新图谱。


## 11. 2026-11-13 体系收束：从关键词集合走向“可解释、可验证的项目关系”（V0.2）

**用户明确确认的新方向**：锚点与映射并非偶然有用的两个词，而是指向完整项目内目标、专业知识、来源、数据、业务、设计、代码、测试、运行与反馈能够相互联系、理解、验证和修正的能力。用户对这一方向的正面反馈，是重要的**需求反馈**，不是已独立证明的模型或研发效率改善。

**为什么此前连续数月的研究容易空转（解释性假设）**：
1. **问题表征过局部**：把普通人的目标马上缩成一个按钮、一条策略或一个专家主题；少考虑完整业务范围、前置条件和隐藏失败。
2. **层次常被混用**：知识分类、项目阶段、来源证据、运行测试、AI能力、市场结果本来不同，却在摘要中被视为同一层“进展”。
3. **资料与实现断开**：搜索许多GitHub成品，却没有充分回答其自身设计问题、数据如何形成、现成代码在哪、为何能改变当前业务判断。
4. **单向报告缺反馈**：从参考资料到总结的单向流容易越写越完整，却缺从失败源码、真实测试、应用效果回到知识与目标的逆向修正。
5. **缺失错误传播的视角**：一个时点或账户语义错误可能同时污染选币、资金网络和盈利模拟，但之前只修当前文件。
6. **反复纠偏被过度固化**：每发现一次遗漏，就建新的阶段、标签、专家制度，而不是回到共享的关系/证据根因。

**为什么这次的解释更贴近用户意图（待实证）**：以“锚定、映射、关系语义、双向追溯、可执行约束、保障论证、变化影响”共同解释整个项目，首次较完整地同时连接了**知识形成、项目组织、真实数据语义、代码行为与可核查结果**；外部成熟项目为每一种机制提供了对应原型，且明确可用与不适用的边界。前面的分析是对用户反馈和既有失败的**竞争性解释**，未排除项目复杂度、可用工具、历史上下文、真实数据许可等其他原因。必须用下一次相同任务/独立材料的对照检验。

### 11.1 七类核心能力：收束后只保留七个“问题”，不新增七个系统

| 汇总能力 | 核心问题 | 主要专业概念 | 现有承载/实际改变 |
|---|---|---|---|
| **S1 方向保持** | 为什么做、谁确认、何时可改？ | 锚定 Anchoring、目标追踪 Goal Alignment、需求分解 Decomposition、ADR 决策记录 | ai-d现有意图理解/发展/选择、用户授权，业务项目原目标与决策台账；不让AI最新建议覆盖已确认目标 |
| **S2 结构理解** | 什么对象、哪种层级、哪个上下文？ | 分层 Layering、抽象 Abstraction、聚合 Aggregation、领域本体 Ontology、限界上下文 Bounded Context、概念消歧 | P1–P8问题与专业领域分开，项目内把Token Account/Owner/Controller等语义区分 |
| **S3 映射对齐** | A与B在哪些条件下真正对应？ | 结构/语义/关系/跨层/动态映射、对齐 Alignment、关联 Linking、知识图谱 Knowledge Graph | 主张级联系，比文件名和关键词更精确；保留映射版本、范围与失效条件 |
| **S4 双向追溯** | 这个结论从何来、修改后影响哪里？ | 依赖 Dependency、双向追溯 Traceability、血缘 Lineage、来源 Provenance、数字线程 Digital Thread | 目标↔实现↔测试、原始来源→处理→主张；有实际运行才可补运行血缘 |
| **S5 契约约束** | 哪些条件不可违反，越界时怎样降级？ | 数据契约 Contract、不变量 Invariant、断言 Assertion、约束传播 Constraint Propagation、语义一致性 Consistency、覆盖度 Coverage | 把知识边界变成API/数据定义、逻辑限制和反例测试；文档警告不是程序执行 |
| **S6 证据保障** | 声称“做到了”实际有何依据？ | 交叉核验 Cross-checking、三角互证 Triangulation、反证 Falsification、保障论证 Assurance Case、回归 Regression Testing、样本外验证 | 对每条主张记录证据链、反例和无法支持的升级；统计Cross-validation不等于多来源三角互证 |
| **S7 演化治理** | 新证据/代码/环境变化应改哪里、何时停止？ | 变更影响 Impact Analysis、传播 Change Propagation、可观测性 Observability、漂移检测 Drift Detection、版本 Versioning、闭环反馈 Feedback、持续改进 Continuous Improvement | 有证据才沿直接关系影响局部，必要时回滚/撤销；避免无穷制度化 |

**最重要的区分**：七类是共同工作的**认知责任**，不是七个软件服务或强制执行步骤。知识九阶段 K1–K9仍回答知识怎样形成与演化；P1–P8仍回答研究什么；具体业务项目继续自己定义产出与安全边界。

### 11.2 全部关联专业术语归位清单（便于外部研究不漏项）

| 家族 | 相关关键词/概念（英文检索同义方向） | 与邻近概念的边界 |
|---|---|---|
| 意图/结构 | Goal Anchoring、Goal Alignment、Layering、Decomposition、Abstraction、Aggregation、Ontology、Bounded Context、System Modeling / Model-Based Systems Engineering (MBSE / SysML) | 目标不是知识目录；系统模型覆盖结构与行为，但不保证运行效果 |

**关键词是资料检索入口，不是要求在运行代码内构建50种节点。** 若某术语只换名字不提供新机制、边界或影响关系，不另建知识单元。

### 11.3 五张逻辑网络与唯一“跨图”语义

1. **目标网络**：用户确认目标、候选解释、业务结果、授权边界；关系如 refines / requires / approved_by。
2. **知识网络**：概念、原始来源、专业主张、方法、竞争假说、反例；关系如 broader / contradicts / applies_to。
3. **数据与事实网络**：真实事件、原始RPC、账户/Owner、行情快照、转换、时间、来源和数据覆盖；关系如 observed_in / derived_from / lineage_of。
4. **工程网络**：已有接口、代码、数据契约、依赖、架构决策、功能开关；关系如 implements / calls / constrained_by。
5. **验证与反馈网络**：测试、真实案件、负例、CI运行、影子分析、业务效果、修订；关系如 verifies / fails_when / triggers_review / supersedes。

这些是**观察同一个项目的五种视图**；可以由一个现有Markdown目录、源代码、SQLite与测试共同承载，绝不等于采购/部署五套图数据库。跨图的连接单元优先是**能改变判断的具体主张**，再沿关系找来源、依赖、实现和可检查的验收。

关系强度必须区分：DIRECT_SOURCE_FACT（有路径/真实证据）、CODE_STATIC_REFERENCE（代码可见）、IMPLEMENTED_BEHAVIOR_TESTED（限定测试）、THEORETICAL_ANALOGY（理论类比）、REVIEW_CANDIDATE（待查影响）、UNKNOWN；**关联不能凭相同标签升级成真实经济同控或因果关系**。

### 11.5 关键关系之间的判别（避免概念混用）

- **Mapping vs Alignment**：Mapping指对象之间的对应规则；Alignment更强调两边定义/条件/粒度是否一致；一份映射可存在但语义对齐仍失败。
- **Link vs Dependency vs Trace**：Link可能只是参考；Dependency表示后续结果确实依赖前项；Trace说明关联路径及其责任/证据；不能由普通链接自动得出需重构代码。
- **Provenance vs Lineage**：前者重在出处、生成过程和使用依据，后者重在输入经过怎样的处理流到输出，二者可重叠但不等价。
- **Ontology vs Knowledge Graph**：本体定义概念和有效关系；图谱表达具体对象/事实/关系，图谱正确连接不表示本体或结论正确。
- **Contract vs Invariant vs Assertion**：契约声明输入/输出及使用条件；不变量是必须保持的业务/算法性质；断言是某个检查位置的可执行条件。写成Markdown不等于已强制执行。
- **Verification vs Validation vs Assurance**：Verification核实现是否符合规格；Validation检验是否满足真实用途；Assurance Case把重要主张、论证、证据和反例组织起来，减少局部测试冒充整体成功。
- **Triangulation vs Statistical Cross-validation**：三角互证比较不同来源/方法是否独立支持主张，统计交叉验证用于估计样本内模型泛化，不是直接证明链上同控；反证关注什么事实会推翻当前解释。
- **Impact Analysis vs Change Propagation**：前者发现可能受影响的消费者；后者是确定并实施必要修改；范围不能无限扩大。
- **Digital Thread vs Runtime Workflows**：数字线程强调跨阶段信息连续性；Agent执行框架负责真实动作和状态，二者不相互替代。

### 11.6 在AI协作项目中的最终收束：七项能力不是新架构

**不更改P1–P8问题索引、K1–K9知识生命周期，也不新建七套知识库。** 在实际任务中，AI先理解目标，然后按需定位当前哪一种关系能力不足：没有来源→回原始证据；语义对不齐→查上下文/概念；有知识却找不到代码→查实现映射；测试通过但主张太强→建证据论证；改一个接口影响其他地方→做变更影响；重复几轮仍无业务增益→用风险锚点停研/切路。

**下一次可验证的实验**：以一个事先未预置“正确专业词”的Blix真实研发任务，在同样仓库版本、来源与预算下，比较(A)只审受改文件 vs (B)基于既有锚点与双向追溯检查。记录重要遗漏/假依赖、正确发现的下游、真实代码/测试变化、人工复核成本、最终业务质量。设失败条件：仅多出图、术语和报告却没有可核新增事实或修复，停止扩张。

**认识锚点**：AI的价值不是“知道很多关键词”，而是知道什么时候应当连接哪些知识与工程事实，哪些关系没有证据，以及新事实改变了什么判断。


## 12. 2026-11-13｜新纠偏：数据源主权与职责归属——不要在AI下游重做上游

**用户新增重要边界**：“尽量不要直接做数据源应该做的，因为没有提高数据源”。这不是放弃核验来源，而是从过去的“下游反复补个例”转向“找到有责任的上游、修复或更换上游能力，让所有下游一起受益”。属于多层锚点的 **责任归属（Ownership）× 反向追溯（Reverse Traceability）× 失效根因（Root Cause）**。

**不可以混为一谈的三种责任：**

| 责任归属 | 应负责什么 | 不应该由谁伪装完成 |
|---|---|---|
| 外部数据供应商 / 协议 | 公布能提供的事实、实际覆盖、时间语义、历史接口、额度和查询边界；源头不覆盖时比较成熟替代源/组合或保留UNKNOWN | AI不应将事后页面、缓存或另一来源估计说成“原供应商完整数据” |
| 我方采集与接入层（Source Adapter / Ingestion） | 在许可/预算内正确接收、去重、持久化、补查、断流恢复、游标/水位、来源血缘与质量警报 | AI报告不应再建私有采集器、另存另一套样本、猜填事实 |
| 确定性解析/专业分析/AI | 解析与守恒、关系候选、竞争解释、下一项取证、结果展示、独立验证和拒绝不支持的结论 | AI不能篡改源头原文；数据源也不必替AI猜操盘身份或跟单利润 |

**“改进数据源”不是承诺修改第三方供应商内部系统。** 真正可改善的是我方选源、授权接入、捕获/存储/恢复、来源契约及供应商服务质量；第三方不存在的字段不能靠换名或AI推断“生成”。

**复杂数据问题时的实际判断**（按需，不是每轮表格）：
1. 从业务错误或UNKNOWN逆向追查最早出错环节：provider → own adapter → storage → deterministic parser → derived evidence → AI → UI。
2. 先核原版Blix、钱包RPC游标/市场订阅/历史记录及成熟供应商；同一职责由既有单一组件承接，避免重复建设。
3. 供应商缺少能力：核实API/价格/许可，先调来源策略，不改模型提示词；未获授权不增加费用。
4. 我方采集器缺陷：在**源层所有者**修断流、漏存、重复、源时间或恢复，不在每个Mint报告局部补丁。
5. 解析器错误：仍由确定性解析修正，不要求供应商替应用完成经济实体与库存假说。
6. 只读审计/单Mint链路是**定位源层失效和验收源层改善的手段**，不能代替生产数据源；必要原文补查要回填有权威归属的上游仓储并可重放，不能塞进模型上下文冒充完整事实。
7. 没有权限或确实无法从来源证实时保留SOURCE_GAP / UNKNOWN / BLOCKED，准确说明对业务的影响。

**进步必须度量源端**：同一可核范围的事件覆盖、断流恢复、历史补查、游标连续性、重复率、到达时效、错误暴露以及对多个下游业务的共同改善。多一段AI解释或人工补齐一个Mint的资料不算提升数据源；供应商全市场分母不可知就保留UNKNOWN。

**与旧锚点的关系**：归入S4双向追溯、S7演化治理，并受S5契约与S6证据保障约束；不新增S8或数据源Agent，不改变已确认项目目标与知识九阶段。通用责任分工在ai-d维护，Blix源码归属/验收在原Blix台账维护。


## 13. 2026-11-13｜纠偏能力的深层扩写：纠错、校准、根因修复与学习（V0.3）

> 用户进一步提出：项目许多地方需要纠错，希望将“纠偏”从口头反馈发展为对目标、知识、来源、设计、代码、评价、AI协作方式都适用的专业能力。**此处扩写既有S1方向保持、S4追溯、S5约束、S6证据保障、S7演化治理**，不新增第八项固定能力、纠偏Agent或机械审批流水线。此论述属于待实证的研究方法，不证明AI已经会主动准确纠偏。

### 13.1 六个容易混用、却决定了修复位置的概念

| 概念 | 真正回答的问题 | 与相邻概念的区别 |
|---|---|---|
| **偏差 Deviation / Mismatch** | 现在观察到的结果，与哪个明确目标、事实、契约或可靠预期不符？ | 与“观点不同/出现未知”不同；缺真值、目标含混时先核准基线，不武断判错 |
| **纠错 Correction** | 先把当前可确认的错误对象改对，或使损害不再继续 | 修复一个报告/字段不等于源头同类问题已经消失 |
| **纠偏 Course correction / Reorientation** | 现有问题理解、研究路径、组件责任或判断方向应怎样调整？ | 可以改变行动或假设，而不一定需要改既有代码 |
| **根因与促成因素 RCA** | 哪些因果条件让错误发生、传播、未被察觉？ | 可能多因共同造成，不应强迫寻找唯一“根因”；来源缺失与解析错误不能混因 |
| **纠正措施/预防措施 CAPA** | 通过什么措施消除已发生问题的机制，提前防止同类潜在失败？ | 需能验证效果；“提醒AI下次注意”通常弱于改变真实数据契约和测试 |
| **校准 Calibration / 漂移 Drift** | 模型判断、指标、源语义、市场分布随时间是否偏离已验证条件？ | 不是所有变化都是错误；先检查基准是否仍适用、目标是否已变 |

**关键判别**：没有权威基线时，不把某个竞争性解释定为错误；未知是一种需要补证的状态，不是可随意“纠正”的假数值。已证实的新事实既可以推翻旧假设，也可以仅缩小其适用边界。

### 13.2 纠偏横跨的九类“错误位置”，不是九个执行步骤

1. **意图与价值偏移**：将普通表达迅速缩成某个按钮、策略或单一Mint；纠正上层问题定义，而不是增加按钮。
2. **问题表征与专家认知偏差**：遗漏经济主体/控制权与地址角色的区分，或将一种行业术语的含义移植到另一行业；应校准专业对象和边界。
3. **知识选择与来源理解偏差**：搜索到项目README就当完整实现；没有读代码、测试、历史变更及真实失败；应回查资料、比较竞争解释。
4. **证据与样本偏差**：来源截断、筛选后的市场队列当全市场、公开但同源的文章当独立反证；要核源头、分母、未观测对象和依赖关系。
5. **供应商及接入责任偏差**：源端断流/接口不支持，却在AI侧重复爬取补一个报告；应先确定供应商/本地接入/存储的真正责任人（见第12节）。
6. **设计/架构及代码偏差**：同一能力被几个模块重新实现、破坏原产品或引入错误数据含义；回到原有代码所有者与可执行约束，而不是再建新服务。
7. **评价与时间偏差**：合成测试通过当主网验证、事后价格当事先可交易报价、只看模型挑中的样本；修正测量与对照条件。
8. **执行/协作/授权偏差**：模型不断报告与建议却没有真正完成已授权任务，或未经授权调用交易/付费服务；前者调整任务选择，后者保持明确边界。
9. **反思与修正机制本身的偏差**：每次用户指出遗漏就升级一套长期强制规则，或纠正后再次原地打转；要检查“纠偏行为是否反过来污染上下文与产品目标”。

**横向错误类型**还包括：时效漂移、模型过度保守/过度自信、状态错级、概念等价误判、错误责任归属、缺陷传播、伪关联、回归破坏、目标污染、反馈迟滞。不能仅以文件名或关键词匹配认定错误因果。

### 13.3 纠偏可以改变哪些深度？单环与双环学习

- **即时止损/遏制（Containment）**：明确错误事实影响的下游，必要时暂停输出不受证据支持的结论；这能防止扩大损害，但不等于修好根因。
- **单环修复（Single-loop）**：在目标、假设和业务定义仍成立时修事实、代码、游标、时间转换或反例测试。例如已确认单位换算错误，只需修换算并回归。
- **双环纠偏（Double-loop）**：如果反复修同类bug仍出错，质疑更上游的假设、来源责任、成功标准或研究入口。例如“有价格就能模拟盈利”前提本身错误，不能再修价格公式。
- **目标层重审（Goal review）**：如果新证据揭示AI自己选错要解决的问题，提出不同解释与选项；**人的重大价值目标需用户确认**，AI不得因双环概念擅自替换长期目的。

借鉴Chris Argyris《Double-Loop Learning in Organizations》（1977，https://hbr.org/1977/09/double-loop-learning-in-organizations）：单环调整行为以实现既定目标，双环检视支配行为的假设/政策。层级越深不一定越好；正常、低风险的bug用直接修复更高效。理论用于解释偏差，不代表已在AI系统里实现自动双环学习。

### 13.4 发现与定位：沿跨层关系找“最早可干预的失效处”

**偏差线索**可以来自用户反馈、实际业务失败、原始事实与报告冲突、质量/覆盖告警、代码变更、同预算对照、反例、外部新知识以及AI自己发现的证据冲突。

有必要时逆向追溯：**实际用户结果 → UI/模型主张 → 业务解释 → 确定性解析 → 存储与索引 → 我方采集 → 外部源与真实世界**，同时回查项目目标/权限。找出“最早能够通过当前权限、工程责任和证据修复的环节”，再检查传播到哪些下游。

- 不因某字段没有值就默认“供应商数据差”：可能是适配器漏字段、过期缓存、索引丢失、查询范围错误或事实本来未公开。
- 不因为有数据就默认“AI误读”：可能是账本重复、同名概念含义不同、用户任务定义未确定。
- 不强迫一次事故只有一个根因：例如源断流、没有水位告警、报告错误地把UNKNOWN当0，三个条件共同造成“无异常”误判，需要按职责分别纠正。
- 选择**可反驳的因果解释**：若只是改下游文案不会使源端补回丢失事件，则该修复只能改变误导程度，不能声称采集缺陷消失。

### 13.5 纠偏的实质行动与独立验收

一项有意义的纠偏至少要清楚：**不符合什么基线；证据是什么；根因/促成因素的竞争性解释；应由谁修；如何修；谁能验证；什么情况下撤销修正。**

修复选择应区分：
- **恢复（Mitigate）**：临时降级显示、标注UNKNOWN、防止传播，以保障当前用户；
- **根因纠正（Corrective）**：修真正的源/解析/设计/测试所有者并验证原错误不再复现；
- **风险预防（Preventive）**：为同类错误增加恰当的数据契约、回归反例、源健康监控或变更影响检查；
- **知识修订（Revise）**：有新证据时原位修订原专业主张与使用条件，不把每次补丁升格为全局提示词。

**三类验收**：
1. **当前实例是否修对**（局部正反例和源码行为）；
2. **同类错误是否减少且未制造其他回归**（影响范围内的功能/数据源/业务回归）；
3. **修复本身是否值得**（错误成本、用户纠正次数、延迟、误报率、运行费用与实际业务成果）。

需要明确时间尺度：静态规则/合成测试只能证明限定行为，真正源覆盖与模型增益要有独立真实观察；受权限阻挡时状态保持UNKNOWN。Google SRE postmortem强调多种促成因素、可验证的优先行动和回顾；ASQ CAPA区分局部修正、纠正与预防措施。来源：
- https://sre.google/workbook/postmortem-culture/
- https://sre.google/sre-book/postmortem-culture/
- https://asq.org/-/media/public/wqm/ASQ-WQM25_RCA.pdf
- https://careers.asq.org/career-resources/on-the-job-3/capa-corrective-and-preventive-action-for-quality-engineer-2026-112

### 13.6 纠偏本身也可能犯错：六项反作用与停止边界

1. **过度纠偏**：看到一次反例就推翻完整专业知识或原产品；应缩小适用条件与真正影响范围。
2. **纠偏振荡**：今天“知识优先”、明天“案例优先”、后天“软件参数优先”，每次用户反馈都被固化成新强制入口；旧知识可以保留，但入口由当前问题与证据决定。
3. **错位修复**：在AI侧补采集、在数据源层猜钱包控制权、在提示词层修代码bug；必须回到权威职责处。
4. **证据过度保守**：要求理论必须先有生产实验才允许初步可逆尝试；根据风险做分级验证，理论互证允许候选决策。
5. **证据过度自信**：来源作者声明、静态代码、离线绿色测试直接升级为真实市场收益/模型质量。
6. **检查负担反超收益**：每个小问题开根因会议、做九阶段、写八类标签；对简单可逆任务直接修并验证，重大/重复/系统性偏差才深审。

**纠偏的终止条件**：有充分证据让当前目标恢复正确方向、相关防复发措施已适当验收，或者证据/权限成本使继续不合理并有明确开放条件。修正不要求零风险，也不能被“还可能有未知错误”无限拖延。

### 13.7 与已有S1–S7、K1–K9、P1–P8的对齐，避免新框架

- 目标错误：S1方向保持 + P1问题形成 + K1规划/必要时K9反向修订；
- 认知/术语错误：S2结构理解、S3语义映射 + P2/P4/P5 + K4/K5；
- 上游数据错误：S4来源追溯、S5契约 + P3/P5/P7 + K2/K3/K8；责任边界见第12节；
- 工程实现错误：S5契约、S6验证 + P6/P7 + K7/K8；
- 方法与持续反馈错误：S7演化治理 + P7/P8 + K9；严重时再回K1；
- 这些是**分析定位关系**，不是必须运行的九步或七个子系统。

### 13.8 三个能分辨“真的纠偏”与“只增加说明”的反例

| 现实问题 | 可能的表面修正 | 真正可验证的纠偏 |
|---|---|---|
| Blix RPC重连期间漏消息，AI称“没有交易” | 手工为这一币补一笔交易、再写一句注意断流 | 源层保留缺口与恢复证据；下游正确降级“不完整”；同一恢复措施服务多个钱包/Mint并有回归 |
| Token接收钱包后来卖出，被称“抛售刚转入筹码” | 改掉“庄家”二字 | 在确定性证据和模型输出中保留库存批次UNKNOWN，建立含旧库存/多入账的反例；不把相近时间升格为同批 |
| AI几个月重复写知识规划但产品没进展 | 加一套“务必执行”的大提示词 | 检查是否项目目标理解偏移、工具与授权缺口、方案复用判断错误；选一个可验收产品任务实际执行，并检验纠错成本是否降低 |

### 13.9 轻量登记：保留因果链而不是增加形式

对于**重大、反复发生、跨模块传播**的偏差，在现有研究/建设台账用一段结构描述即可：
**偏差观察与用户价值 → 证据/源版本 → 主张的正确基线与不确定性 → 直接受影响锚点/代码 → 可检验原因（若未知标假说） → 责任组件/授权 → 已实施修正 → 对照与反例验收 → 仍未完成/复开条件**。

按“真实风险、重复频率、跨层传播范围、纠正后的公共收益、成本与授权”选择优先事项。不根据锚点数量、报告篇数或发现的表面异常数排序。独立评测应比较“局部修复”与“纠偏至首个有责任的源层/假设”，不能让同一模型同时生成、评审并宣布成功。

**最重要的结论**：纠偏不是另一套专业制度，而是让AI持续具备“发现偏离—检验解释—选正确责任处—实施可逆修复—验证效果—撤销失效认识”的判断与行动能力。其真正成功需要在下一个真实任务上验证。
