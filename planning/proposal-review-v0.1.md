# 重要方案如何经过多轮推演，再进入实施？｜候选 V0.1

> 2026-11-06｜方案治理草案。目标是防止过早建设和钻牛角尖，同时阻止“永远规划不执行”。这里的轮次是**思考用途**，不是必须重复执行的程序。

## 一、为什么要有多轮规划？

七月至十一月的研究已反复出现：有时太快把好想法设计成模块、专家制度或长提示词；有时又在修订旧知识的循环中丢失真正的业务目标。此问题首先是**目标-证据-选择-实施之间缺少可追溯关系**，不只是项目文件夹太乱。

可借鉴但不照搬的成熟思路：
- NASA 系统工程：从利益相关者期待到具体需求、验证方式的关联和变更管理。来源：https://swehb.nasa.gov/spaces/SWEHBVB/pages/32604503/SWE-050%2B-%2BSoftware%2BRequirements
- Argyris 双环学习：不仅修正具体行动错误，也应检验决定行动的既有假设和目标。来源：https://hbr.org/1977/09/double-loop-learning-in-organizations
- 决策记录 ADR：保留背景、选项、选择理由与结果；选择改变时解释取代关系。来源：https://github.com/architecture-decision-record/architecture-decision-record
- Cochrane 研究范围与问题形成：研究问题先于资料搜索和证据综合。来源：https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-02

这些原则用于指导个人 AI 研究项目，不是说整个项目应当执行完整航天工程或临床系统综述流程。

## 二、三种方案的第一次比较

| 模式 | 做法 | 好处 | 在 ai-d 的风险 | 初步裁决 |
|---|---|---|---|---|
| A 固定多轮审批 | 每个任务三轮分析、专家打分、批准后执行 | 重要问题可能审查充分 | 简单任务流程爆炸，后续过度约束 | 不作为默认 |
| B 自适应评审与适量行动 | 重要方向多角度审查；可逆小事项直接做；审查发现实质变化才延伸 | 能在专业性、时间成本与行动之间平衡 | AI 可能自行判断何时足够 | **首选候选** |
| C 先做再改 | 快速原型、依据运行反馈调整 | 真实反馈快 | 把未经评估的原型/架构过早固定，浪费迁移成本 | 仅用于低风险可逆试验 |

## 三、第二次推演：从不同专业角度主动挑战 B

| 视角 | 要挑战的问题 | 导致的修订 |
|---|---|---|
| 用户/产品视角 | 是否让人反过来学习复杂表格才能指挥 AI？ | 简单自然语言仍是入口；AI 自己整理专业选项 |
| 管理与决策视角 | 规划会否永远扩展新目标？ | 每项高价值新方向记录与 G0–G2 关联及取舍 |
| 研究与证据视角 | 证据不够时是否强行下结论？ | 区分现有事实、候选假设、待验证关键未知 |
| 工程视角 | 是否重造成熟运行时/文档架构？ | 先查现有库、成熟工具和复用路径，确有缺口再开发 |
| 知识治理视角 | 每次分析是否新增一份互不关联的文件？ | 先在原位置修订；一次决策只保留一个权威当前入口 |
| 质量评测视角 | “想了很多轮”是否真的提高结果？ | 只有反证/重要比较改变路线时才值得额外投入 |

**关键修正**：多轮循环的目的不是多出几个版本号，而是测试**当前理解能否经受不同证据和专业立场的挑战**。

## 四、第三次收束：B 的可落地形式

**复杂、跨域、高影响、难回滚的方案**，通常做三种不同性质的思考：

| 审查 | 应产生什么独立增量 | 已充分的迹象 |
|---|---|---|
| 形成候选 | 问题模型、成功标准、可行方案与竞争解释 | 至少两种真正不同的路线或明确只有一个可行解 |
| 反向挑战 | 最可能失败的条件、未查的资料、重复建设、目标冲突 | 关键反证已检索或已标记为可接受未知 |
| 实施推敲 | 最小可交付成果、授权、回滚和核查方式 | 可以立即开展可逆、价值高的下一动作 |

**普通、低风险、可逆任务**可以完全跳过正式多轮方案文档。遇到重大改变或者证据矛盾，重新进入对应的审查，而不是全部从头做起。

### 提前规划的停止条件（避免钻牛角尖）

满足以下条件就应转入最小可验收行动：上层目标和当前任务的关系清楚；主要竞争路线已比较；最大风险可管理或已明确告知；额外搜索无法合理预期改变当前可逆决定；有实际验收方法。若不满足关键条件，则继续获取**能够改变决定的信息**，而非扩大无关研究。

## 五、把第一次方案演化明确写出来

本次起点不是一个确定技术架构，而是用户连续提出的需求：
1. GPT 研究好的专业知识，应能可靠进入 GitHub，并在上传后正确组织维护。
2. 从初始意图就要识别上层与中间目标，防止扩张偏题。
3. 实施前要从多种成熟专业思维提出多版候选、挑战和修订。
4. 不能因流程复杂而迫使人自己管理，AI 应承担专业工作。

**第一版（过度简单）**：“研究完成 → 新增 Markdown → GitHub。”遗漏目标关系、去重、证据等级和上传后的维护。

**第二版（过度复杂风险）**：“统一流程中心＋专家审查组＋动态目标状态机＋自动机器人上传。”这些功能未经证实需要，可能复活过去的复杂化问题。

**第三版（当前候选）**：“现有 GPT + GitHub；目标导航＋选择性多轮评审＋知识分类/核实＋草案 PR＋核查回读；在真实任务发现系统缺口后再评估自动化。”这一版本**兼顾可行动与可回退**。

不是经过了三次实验，也不是三个不同模型的独立评审：这是同一研究中的三次方案推演。真实改进仍须通过任务结果检验。

## 六、职责清楚，但不扩建专家 Bot

| 职责 | AI 应承担的工作 | 与其他职责的交接件 |
|---|---|---|
| 目标判断 | 恢复人原话、目标层级、变化与成功条件 | 目标导航结论 |
| 研究调查 | 定义证据问题，获取书籍/标准/论文/代码等合适来源 | 原始来源＋具体主张 |
| 综合裁决 | 找竞争解释、重复内容、冲突和可行方案 | 方案比较与推荐 |
| 知识编辑 | 更新标准概念、对应问题、适用边界与链接 | 已核对知识条目 |
| GitHub 交付 | 比较差异、在正确路径新增或修订、提交、回读 | commit / PR / 变更摘要 |
| 验收与反思 | 检查结果、错误、成本，选下一项有价值的工作 | 证据化状态与下一步 |
| 用户 | 提供真实反馈、价值判断、重大方向与必要权限 | 关键选择或停止指令 |

以上是**责任分工，不是必须创建七个 Agent**。同一模型可根据任务执行多种职责；只有出现有证据的并行/权限/能力需求时才考虑分离。

## 七、下一步的真实验收

至少找两个差异明显的任务：A 为跨领域专业知识整理，B 为某个实际软件/业务方案选择。记录无规划基线、B 方案的成果，观察目标偏差、实际错误、重复文件、人工返工、总时间和是否及时交付。只在实际观察到改进时把方法提升为跨任务 Skill。

最终裁决状态：**PROPOSED**。用户此前确认的是“减少专业指挥负担、保留探索空间、知识优先正确运用”的目标，不是本文件中每个操作细节已经获批。
