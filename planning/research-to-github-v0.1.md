# 从 GPT 研究到 GitHub：知识交付、排版、验收与维护方案｜候选 V0.1

> 2026-11-06｜草案。已有 GitHub 仓库：https://github.com/sunshihao001/ai-d （目前 Public）。本文件不自动启动后台上传；本项目在 GPT 中的研究仍需实际可用的 GitHub 工具、当前访问权限与适用授权才能同步。

## 1. 回答最直接的问题：研究完成后会不会自动上传？

**不会仅因为 GPT 说“研究完成”而自动同步。** GitHub 写入是一个**独立、可核查的动作**。当用户已授权本项目范围内的 GitHub 写入，且连接器可用、内容适宜公开时，AI 应主动完成上传并回读核验，而不是要求用户自己复制粘贴。

如果在当前会话缺少 GitHub 写入工具、授权或验证能力，只能明确报告“尚未上传”；提供可检查的文件或提交计划，不能声称后台稍后会完成。长时无人值守同步未来需要独立的触发/运行机制，不把聊天回复当持续运行服务。

## 2. 从研究到交付是一条可回退的关系链

`原始想法/任务 → 目标与问题 → 相关来源 → 证据和解释 → 成熟方案与反证 → 知识分类/与既有内容比对 → 草案/审核 → GitHub 写入 → 回读/链接验证 → 使用反馈 → 原位修订`

这条链是**责任和证据追溯路线**，并不意味着简单问答必须经历每一阶段。

### 什么内容值得上传？
| 成果类型 | 如何处理 |
|---|---|
| 无新实质增量、只重复旧答案 | 不新增文件；必要时修订现有段落 |
| 与长期目标有关的新概念/理论/方法 | 先比较现有知识索引，追加独立的新机制、来源、反例 |
| 深度原始研究报告 | 放在 research，引用已有知识条目；报告不是最终权威规则 |
| 改变重大方向的方案决策 | 放在 decisions，保留选项、证据、裁决、后果、可推翻条件 |
| 真正的任务结果与对照评测 | 放在 evaluation，注明运行环境、事实来源、样本和未完成 |
| 目标导航和交接方式 | 放在 planning；先草案评审，别直接变成全局提示词 |
| 隐私、敏感数据、未经许可的整篇作品 | **不写入公开仓库**；可在受控环境留来源指针或非识别化抽象 |

**原则**：研究成果有价值才提交；上传不等于结论正确、Skill 已接入或模型能力变强。

## 3. 沿用现有结构，不另建“知识行政系统”

| 现有位置 | 唯一职责 | 建议形式 |
|---|---|---|
| `README.md` | 项目定位和统一导航入口；保持简短 | “为什么/从哪里开始/当前状态” |
| `knowledge/INDEX.md` | **当前可用知识的主索引**，按根本问题 P1–P8＋学科标签、关系跳转 | 分类/链接，不重复完整正文 |
| `knowledge/foundations/` | 成熟学科概念、理论、方法和适用条件 | 主题综合文档；先修订、少建文件 |
| `knowledge/source-register-*.md` | 原始标准、书籍、论文、源码与来源定位 | 来源与支持的具体主张；核验状态 |
| `research/` | 从问题到证据的探索、方案对照、开放假设 | 保留过程与边界；可多版本 |
| `decisions/` | 为什么某条路线被选中或否决 | 少量重要决定记录（ADR 思路） |
| `evaluation/` | 实验与错误反馈、实际能力增益核验 | 区分设计/离线/真实运行/独立评测 |
| `planning/` | 目标、实施方案、交接及恢复原则 | **本轮新增的候选文件**，不含专业研究全文 |

**不要因为有8个问题域就建8棵目录树。** 先一个索引＋少量主题正文，用链接和标签跨域连接。既有目录中重复概念通过索引收束，不直接删除任何未经审查的历史资料。

### 文档排版与写作方式

按读者目的借鉴 [Diátaxis](https://diataxis.fr/)：解释为何（研究说明）、怎样做（操作指引）、可查询定义（来源和规范）、如何学习操作（示例/案例）。**这是阅读和维护视角，不强制建立四个新目录。**

- 文件名简洁且含义稳定：英文小写连字符较适合跨工具路径；中文标题在文件内。
- 首屏先提供：研究问题、结论/当前状态、证据等级、日期；长文有导航或主题小节。
- 重要主张附近放**指向原始来源的链接**；说明来源实际支持到什么程度。
- 不复制整本书、私人对话、整篇付费论文；不把 AI 猜测作者动机写成事实。
- 当同一主题已有正文，只在其原位置修正，必要时新增章节；比较不同观点时可保留冲突状态。
- 一个决策文件记录一件有长期影响的决定。研究报告不自动升格为治理规范。

## 4. 每次实际上传的操作与核查

**A. 写入前：**
- 确认仓库/分支/公开状态、权限与用户授权范围；
- 读取 README、知识索引和目标路径，找重复、相邻、冲突的已有条目；
- 检查来源和敏感信息；选择“原位修订、交叉引用、合并、保留为草案、不上传”之一；
- 重要结构改变先准备差异预览、评估其他可行布局。

**B. GitHub 写入：**
- 重要规划/多文档整理：优先独立分支＋Draft PR，让变更可审阅，不直接改 main；
- 获准的常规小修可直接修改既有文件，但要保存原版本/提交哈希；
- 对同一路径的更新使用当前版本 SHA，避免覆盖其他并行修改；发生冲突重新拉取比较，不强制推送；
- 文件完整写入后获取 commit SHA / PR URL；Git 历史提供回溯，但不能取代知识内容的来源说明。

**C. 上传后实际验收：**
- 从 GitHub **重新读取**每个改动文件，而不以写入 API 返回“成功”作为唯一证据；
- 核对内容、Markdown 结构、索引入口、站内相对链接、来源链接与实际目标分支；
- 检查没有遗漏历史知识、没有无意覆盖用户目标、没有把未验证内容写成已证实；
- 重要变更通过 PR 审阅后再合并；不将“Draft PR 存在”说成 main 已上线。
- 报告：已上传文件与 commit/PR、已验收部分、失败与 UNKNOWN、下一项高价值工作。

**D. 后续维护：**
- 新证据出现时先定位受影响的现有主张；记录是补充、反驳、替代还是无变化。
- 修订原文并链接旧版来源/PR；对已经被替代的知识保留历史而停止默认引用。
- 当用户目标改变，先修改目标引用和相关决策，不要全库重新生成。
- 当重要方案质量退化时，以失败案例修订方法；不要补上更多全局规则作为自动反应。

官方操作依据：[GitHub PR 基础](https://docs.github.com/en/pull-requests/get-started/about-pull-requests)、[GitHub 分支与提交](https://docs.github.com/en/pull-requests/concepts/writing-code-for-a-project)、[ADR 决策记录](https://github.com/architecture-decision-record/architecture-decision-record)、[W3C PROV-O](https://www.w3.org/TR/prov-o/)。

## 5. 从“职责”而不是“Bot 数量”划分工作

| 交接界面 | 必须包含 | 谁承接 |
|---|---|---|
| 自然语言 → 目标/研究 | 用户原意、当前目标、变化与判断依据 | AI 目标分析 |
| 研究 → 专业综合 | 原始来源、来源支持的主张、竞争解释与未知 | AI 证据与知识综合 |
| 综合 → 内容编辑 | 主要问题分类、原有知识的位置、拟新增/修改、适用边界 | AI 知识维护 |
| 编辑 → GitHub | 具体路径、对比旧版的差异、公开性和目标分支 | AI GitHub 操作 |
| GitHub → 验收 | commit/PR、回读结果、链接状态、未解决问题 | AI 质量检查 |
| 验收 → 下一研究 | 什么知识改变判断、哪个目标可能调整、是否值得继续 | AI 主动研判／人在重大选择时决定 |

这些职责可以由当前 GPT 在一次任务中完成，不要求七个独立 Bot。未来需要并行、多模型交接或长期调度时，再把具体职责包装成 Skill/Agent。

## 6. 一个真实的纠偏例子

**用户提出**：“旧知识系统回答变差，把七月研究整理好。”

不应做：从全部历史文件生成一套新“最强总指令”，上传一批重命名知识卡，再宣布认知升级。

应该做：
1. 还原用户的目标：恢复对专业问题理解与独立研究的能力，减少旧规则锚定；
2. 查历史母本、现有分类和以前失败样本，区分“认知方向保留”与“旧工作流程停用”；
3. 形成竞争解释：提示约束、检索无关、证据缺失、任务变化、模型自身波动；
4. 先修订已有相关条目和来源/冲突状态，保留原文位置指针；
5. 把可公开、非敏感的综述放入恰当目录，通过草案 PR 交付并回读；
6. 选新的任务独立评价是否少了错误和负担；没验证前不宣称能力提升。

## 7. 完成定义与非目标

**一次知识交付真正完成**：目标明确；知识没有重复覆盖；来源可追；选择有依据；GitHub 正确写入；文件回读和链接确认；已报告当前状态与需要再次研究的关键未知。若本次没有新知识价值，则正确结论是“不提交新文件”。

**不是本期目标**：自动监控所有聊天、无审批持续公开上传、完整数据库/图谱引擎、要求用户编程或手工管理全部文档、强制运行全套专家审查。
