# 2026-11-15｜从“思想”到“复杂全域系统”：ai-d 的系统级设计收束 V1.0

> 状态：DESIGN_SYNTHESIS / CURRENT HYPOTHESIS / NOT_IMPLEMENTED_AS_A_WHOLE
>
> 本文件承接 2026-11-15 最近几轮关于“普通人 + 不普通的 AI”“不会就学习优秀知识”“能力整合”“Hermes Runtime”的研究。
>
> 重要修订：能力整合不是 ai-d 的全部，也不是一个简单的中间层。ai-d 实际上是一个跨目标、知识、研究、能力、工具、运行时、领域、证据、工程、评测、学习和人类授权的复杂系统。

## 1. 从一句思想到一个真实项目

当前思想可以压缩成一句话：

> 普通人只需要表达自己想做成什么；如果 AI 不知道，就去寻找优秀知识和已有能力学习；理解后把能力组织起来执行；结果不对就修正，证据不足就停下来，目标改变就重新判断。

这句话是产品哲学/总目标，不是产品架构。

真正实现它，至少涉及：
- 人的意图和长期目标；
- 问题表征；
- 当前状态、未知与知识缺口；
- 外部知识发现、可信度与适用条件；
- 能力发现与能力描述；
- 模型、Agent、Skill、MCP、工具、软件、数据的选择；
- 多能力组合；
- 领域专业知识；
- 执行、权限、结果验证和失败恢复；
- 目标漂移；
- 知识更新、废弃与污染控制；
- 经验沉淀；
- 评测与反证；
- 人类最终授权与价值判断。

因此，ai-d 不能继续被理解成“一个知识库 + 一个 Skill + Hermes”。

更准确的是：

> 一个以人的真实目标为中心、能够不断学习和调用外部能力，并通过现实结果反过来修正自身的开放式 AI 协作系统。

## 2. 为什么能力整合只是核心机制之一

能力整合回答的是：为了这个目标，现在需要什么能力，哪些已有能力可以组合？

但它前面还有：这个人到底想完成什么？
后面还有：组合真的解决了吗？
再后面还有：这次结果是否应该改变以后怎么做？

因此整体关系更接近：

Human Intent → Goal / Problem → Situation / Epistemic State → Knowledge & Capability Gap → Learning / Discovery → Capability Selection → Composition → Execution → Evidence → Verification → Revision → Experience → Future Capability Selection

其中每个箭头都可能需要独立的专业知识和工程机制。

所以不要把整个项目压扁成 Capability Integration Layer。

## 3. ai-d 应该是多层系统，而不是一个核心算法

### A. Human / Goal Layer
解决真实目标、长期目标、当前目标、价值取舍、约束和授权。

### B. Problem Formation Layer
解决普通语言到专业问题的转换、错误前提、关键未知、问题边界。这里继承 P1。

### C. Epistemic / Evidence Layer
解决我们知道什么、为什么知道、来源是否适用、事实/推论/假设/UNKNOWN 的区别，以及新证据是否推翻旧判断。这里继承 P2、P3、P5。

### D. Knowledge Learning Layer
解决“我不会怎么办”：找优秀知识、成熟项目、真实案例、失败案例和专业方法；理解机制、判断适用条件、比较已有认知，并决定什么值得长期保存。

### E. Capability Discovery Layer
解决“我知道目标，但不知道需要什么能力”。能力来源包括模型、Agent Runtime、Skill、MCP、API、软件、GitHub 项目、专业方法、数据源、人类专家和用户自身能力。

### F. Capability Selection / Composition Layer
解决为什么选 A 而不是 B、一个能力是否足够、组合是否互补、失败后是否替换，以及何时继续整合反而增加污染和复杂度。

核心原则是 Minimum Sufficient Capability Set：完成当前目标所需的最小充分能力集合。

### G. Runtime / Execution Layer
Hermes 等 Runtime 在这里。负责模型、Skill、MCP、Browser、Terminal、文件、API、子 Agent、调度、状态、权限和恢复。

Hermes 是重要候选 Runtime，但不是 ai-d 的思想本身。

### H. Domain / Project Layer
同一个通用 AI，在 Solana、软件工程、制造业、学习、职业、市场研究、商业和个人事务中需要不同专业结构。通用机制与领域知识必须分开，避免领域污染。

### I. Verification / Evaluation Layer
区分 Tool 成功、Workflow 成功、输出生成、事实正确、目标完成和用户真正受益。最终评价围绕真实目标。

### J. Learning / Experience Layer
把真实结果转成以后可用的经验：什么能力有效、什么组合有效、什么条件下有效、为什么失败、哪个判断应修正、哪个知识应废弃、哪些经验不能跨领域迁移。

### K. Governance / Human Authority Layer
贯穿整个系统：权限、成本、隐私、对外行动、不可逆操作、价值判断、风险、用户确认和责任边界。

## 4. ai-d 是关系网络，而不是一条固定流水线

暂时可以理解为：

Goal ↕ Problem ↕ Knowledge ↕ Evidence ↕ Capability ↕ Provider ↕ Composition ↕ Execution ↕ Result ↕ Evaluation ↕ Experience ↕ Goal revision

同时存在 source、applicability、dependency、conflict、alternative、authority、freshness、verification、failure mode、cost、reversibility 等横向关系。

现在没有必要提前决定数据库或 Graph 技术。

## 5. “不会就学习”本身也是一个复杂决策

AI 不知道时不应该默认继续搜索。

- 缺一个事实 → 查可靠来源。
- 缺一个专业概念 → 找专业资料、标准或专家方法。
- 缺一个成熟实现 → 找 GitHub、产品或开源项目。
- 缺真实行为证据 → 找数据、运行结果、案例或实验。
- 来源冲突 → 比较来源、适用条件和反证。
- 知识无法决定 → 做可逆实验。
- 信息价值很低 → 停止研究并行动。
- 关键决定取决于用户价值取舍 → 交还用户。

因此 Learning itself needs judgment。这也是为什么 ai-d 不能简单变成自动搜索 Agent。

## 6. 优秀知识不是静态资产

知识进入系统后应经历：发现 → 理解 → 适用性判断 → 当前使用 → 真实验证 → 经验化 → 持续验证 → 更新 / 降权 / 废弃。

旧知识可能正确但过时、只适用于某领域、理论正确但解决不了当前问题、曾经有效但环境已变、与新证据冲突，甚至本来就是错误推论。

这直接连接 ai-d 已有的知识生命周期、P8 污染、纠偏和证据状态。

## 7. 多领域是这个项目真正的难点

如果只做 Solana，很多东西可以硬编码。如果目标是让普通人面对未知问题也能使用 AI 世界的能力，就必须区分通用方法和领域事实/方法/能力。

可以迁移的候选包括：目标理解、问题形成、证据判断、竞争解释、方案比较、失败纠正、信息价值、能力发现、能力替代、结果验证。

不能直接迁移的包括 Solana 钱包行为、激光切割安全参数、医疗判断、法律结论、某个软件 API、某个市场交易规则。

## 8. Blix 是现实实验场，不是 ai-d 本身

Blix 同时涉及链上数据、市场数据、钱包行为、资金路径、软件工程、数据可靠性、AI 判断、产品设计和实时监测，因此适合检验通用整合思想。

但 Blix 成功不能直接证明思想适用于所有领域。必须再选择完全不同的领域。

## 9. 测试方式必须从“回答质量”升级到“完整链路”

输入是普通人一句自然语言。

中间检查：是否正确恢复目标、发现真正缺口、找到合适知识、找到合适能力、组合得当、避免不必要复杂度、发现错误并在必要时改变方向。

输出检查：是否真的完成目标、用户是否少做专业工作、是否减少返工和错误、是否发现重要问题、证据是否可核查、失败后能否恢复、有效经验能否留给下一次。

## 10. ai-d 的长期资产

1. Conceptual Asset：专业思想、概念和边界。
2. Capability Asset：世界上有哪些成熟能力以及如何使用。
3. Decision / Composition Asset：什么情况下选什么、如何组合、何时替代和停止。
4. Evaluation / Experience Asset：什么真的有效、为什么有效、何时失效、如何验证。

真正可能形成长期价值的，是 3 + 4，而不是文档数量。

## 11. 不能把“别人复制不了”说得过头

单个组件可以复制，公开知识也可以复制。潜在差异来自长期真实任务中形成的、经过验证的能力—决策—评测经验，以及失败条件和替代关系。

这仍是潜在壁垒假设，不是已经证明的商业护城河。

## 12. 开发方式也需要改变

不要先把完整系统设计完再开发，而应：最小真实闭环 → 发现缺口 → 研究缺口 → 补能力 → 验证 → 抽象。

当前可作为开发方向：
- Phase 0：思想与边界，已经基本形成。
- Phase 1：自然语言目标 → 学习/搜索 → 能力调用 → 执行 → 验证的最小真实闭环。
- Phase 2：能力发现与替代。
- Phase 3：至少两个差异明显的真实领域。
- Phase 4：沉淀有效组合、失败组合、适用条件和验证结果。
- Phase 5：减少人工指定能力的依赖。
- Phase 6：只有真实运行证明 Runtime 不够时，才决定是否独立产品化或修改 Hermes。

这些是开发方向，不是强制工作流。

## 13. 当前工程原则

- 不要一次建完整系统，因为很多数据结构和 Runtime 边界尚未被真实任务证明。
- 不要把思想直接写成巨大 Prompt；Prompt 不能替代状态、证据、权限、运行、验证和经验。
- 不要把所有知识注入上下文；当前目标需要什么就取什么。
- 不要把每次错误变成新规则；先判断错误根因属于知识、问题表征、能力选择、工具、验证、权限、Runtime 还是目标变化。

## 15. 最近几轮学习后的 ai-d 定义

> 建立并研究一个能够把“普通人的真实目标”和“世界上已经存在的大量知识与能力”连接起来的开放式 AI 系统。

思想很简单：不会就学习，知道就利用，失败就修正，证据不足就停。

实现却是复杂的跨领域系统工程：人、目标、知识、研究、证据、能力、模型、Agent、Skill、MCP、工具、领域、执行、验证、记忆、学习、权限和真实世界反馈必须共同工作。

## 16. 当前真正应该研究的问题

1. 思想是否真的减少普通人的专业负担？
2. AI 能否在不知道时找到真正有用的知识，而不是堆资料？
3. AI 能否把知识转换成当前目标真正需要的能力？
4. 动态能力选择是否优于普通 Agent Workflow？
5. 能力组合是否产生额外价值？
6. 机制是否可以跨领域迁移？
7. 经验沉淀是否改善下一次任务，还是造成污染？
8. Hermes 是否已经足够承载它？
9. 哪些部分必须程序化，哪些只需要强模型？
10. 复杂度增加到什么程度后开始伤害用户？
11. 用户是否真的从“不会”变成“能做成”，而不是变成新的 AI 管理员？
12. 长期积累是否形成真实产品或职业价值？

## 17. 2026-11-15 之后的建设原则

> 不再让架构先决定现实任务；让真实任务反过来决定需要什么架构。

第一项高价值工作不是开发完整 ai-d，而是选择一个完整、真实、可验收、且不同于 Solana 的任务，让系统尝试：普通人一句话 → 自己发现不知道什么 → 找优秀知识 → 找已有能力 → 组织能力 → 执行 → 验证 → 修正。

记录每个真实缺口：哪一步模型已经能完成、哪一步 Hermes 已经完成、哪一步 Skill 已经解决、哪一步需要外部知识、哪一步需要新机制、哪一步只是我们想复杂了、哪一步真正需要 ai-d。

最终让现实任务反过来塑造系统，而不是让预先设计的系统逼迫现实任务适配它。

## 结论

思想与项目必须分开。

> 思想：我不懂，就让 AI 去学习世界上优秀的知识；学会以后，用这些能力帮我把事情做成；做错了，就重新学习和修正。

> 项目：把这句话实现为一个能够处理目标、知识、证据、能力、工具、运行时、领域、执行、验证、学习和人类授权的开放式复杂系统。

这正是 ai-d 下一阶段真正要解决的问题。

## 18. 2026-11-15 紧急纠偏：用户界面极简，系统内部复杂

这次进一步明确一个产品边界：

> **普通人只跟聊天窗口说话；能力选择、组合、验证、纠正、记录、停止等全部属于系统内部机制。**

因此当前不应先做“能力地图”或让用户理解 Capability Graph、Skill、MCP、Runtime 等内部概念。用户的主要接口只有自然语言目标、必要的澄清、结果和系统在关键节点给出的停机说明。

目标体验：

```text
用户：我想把一件事做成
        ↓
系统内部理解目标
        ↓
系统自行发现知识/能力缺口
        ↓
学习 / 选择 / 组合已有能力
        ↓
执行
        ↓
验证
   ↙         ↘
成功         不确定/失败
 ↓              ↓
交付       记录原因 + 停止/修正/请求用户
```

这不是说系统内部不能存在能力地图，而是**能力地图首先应是内部基础设施，不能成为普通人的操作负担**。

## 19. 当前最高优先级：验证与停止，而不是继续扩充能力组合

近期真实 Agent 使用经验反复暴露四类基础失败：

- 做错了仍继续执行；
- 状态丢失后无法可靠续接；
- 无法追溯究竟哪一步导致错误；
- Agent 自行改变目标。

因此 ai-d 现阶段不应继续以“增加更多能力”作为第一优先级。

必须把两个行为先变成**可执行机制**：

### 19.1 不确定就停

当系统发现关键结论、关键输入、关键工具结果或目标解释不足以支撑下一步时：

1. 不得把 UNKNOWN 当成事实继续推进；
2. 判断是否存在低风险、可逆的补证动作；
3. 若补证成本合理，则先补证；
4. 若无法可靠补证，则停止当前链路；
5. 明确告诉用户：
   - 停在哪里；
   - 为什么停；
   - 缺什么证据/信息；
   - 已经完成了什么；
   - 下一步有哪些选择；
   - 哪些部分只是推断而不是事实。

“停止”不是失败，而是系统的正常输出状态。

### 19.2 可追溯

每一次真实执行至少应该能够回答：

- 用户原始目标是什么；
- 系统当时理解成什么；
- 当时依据了哪些知识/证据；
- 选择了哪些能力；
- 为什么选择；
- 发生了哪些工具/模型调用；
- 每一步得到什么结果；
- 哪一步产生异常或不确定；
- 是否发生目标变化；
- 谁/什么触发了修正；
- 最终为什么成功、失败或停止。

这不意味着现在就设计完整数据库或复杂 Trace UI。

第一阶段只需要证明：

> **真实运行结束后，人能够回放并定位关键决策和失败点。**

## 20. “不自造目标”成为硬约束

系统可以：
- 解释用户目标；
- 发现实现目标所需的子问题；
- 提议更好的路线；
- 发现用户没有意识到的风险。

但不能无依据地把：
- 子任务；
- 假设；
- 系统偏好；
- 工具方便；
- 模型自己的兴趣；

升级成用户的新目标。

如果下一步需要改变目标，而不是仅仅改变方法，必须：
- 明确标记“目标变化”；
- 让用户决定，或在明确授权范围内继续；
- 记录变化原因。

## 21. 第一阶段闭环：只做一个最小可执行行为集

当前不要先实现完整 Capability Integration。

先验证以下闭环：

```text
自然语言目标
   ↓
目标理解
   ↓
调用已有能力
   ↓
执行
   ↓
证据/结果
   ↓
验证
   ├── 足够 → 完成
   ├── 可补证 → 补证后再判断
   ├── 方法错误 → 修正方法
   ├── 目标不明确/发生变化 → 请求用户
   └── 关键不确定且无法消除 → 停止并解释
```

**其余整合层设计从这些真实运行中长出来。**

换句话说：

> 先证明“系统会不会正确停、能不能解释为什么停、能不能回放自己怎么走到这里”，再研究“系统应该如何越来越聪明地组织更多能力”。

## 22. 第一阶段验收指标

至少记录：

| 指标 | 要回答的问题 |
|---|---|
| Goal Fidelity | 有没有擅自改变用户目标？ |
| Uncertainty Stop | 关键不确定时是否真的停？ |
| Stop Explanation | 用户能否理解为什么停？ |
| Traceability | 能否回放关键决策和执行链？ |
| Recovery | 出错后能否定位上游并修正，而不是继续污染下游？ |
| State Continuity | 中断后能否恢复到正确状态？ |
| Evidence Boundary | 有没有把推断冒充事实？ |
| User Burden | 用户是否仍被迫管理复杂的 AI 中间层？ |

这些是**第一阶段行为验收指标，不是永久固定的评测体系**。

## 23. 当前系统分类的进一步收束

为了避免“全方面”变成无边界堆分类，当前暂时把知识与系统问题收拢成六个互相连接的主域：

### I. Human & Goal
人、意图、长期目标、当前目标、价值、约束、授权、目标变化。

### II. Knowledge & Epistemics
知识获取、研究、来源、适用性、证据、UNKNOWN、冲突、时效、知识生命周期、污染和废弃。

### III. Capability & Method
模型、Agent、Skill、MCP、工具、软件、专业方法、能力发现、选择、组合、替代、最小充分能力。

### IV. Runtime & Execution
Hermes、状态、调度、调用、权限、文件、浏览器、API、子 Agent、恢复、成本。

### V. Domain & Reality
Solana/Blix、软件工程、制造业、职业、学习、商业等领域，以及真实环境中的数据、约束、反馈和结果。

### VI. Verification & Evolution
验证、评测、停止、追溯、失败定位、纠正、经验沉淀、迁移、更新、废弃和系统演化。

这六个主域是**导航和收拢方式，不是六层固定流水线**。它们与既有 P1–P8、知识九阶段、跨层锚点并存，但不新增新的强制框架。

## 24. 当前开发纪律

从现在开始，除非真实运行证明需要，否则：

- 不先开发能力地图 UI；
- 不先开发完整 Capability Graph；
- 不先设计巨型 Agent Workflow；
- 不先修改 Hermes 核心；
- 不先建立庞大的自动学习系统；
- 不因为出现一个新概念就新增一个分类；
- 不把一次错误直接固化成永久规则。

优先顺序改为：

> **真实任务闭环 → 验证 → 停止 → 追溯 → 失败定位 → 修正 → 再观察缺口 → 再决定是否需要新的整合机制。**

这条纪律本身也不是永久规则；如果真实运行证据证明需要调整，应由证据推动修订。

## 2026-11-25｜原始目标与组织智能的统一

**认知收束（用户确认方向，不改原始目标）。** 从历史研究可见，知识管理、工作流、智能体、技能、专业认知和主动信息侦察各自解决一部分问题，但不能以其中一项替代项目整体。ai-d 的长期目标仍是让人以自然语言提出真实想法和目标，AI 主动学习、发现、组织并运用所需专业能力，在授权内完成现实工作，依据结果修正。目标以人为中心，日常研究与建设责任以 AI 为主；用户保留重大选择及参与专业研究的权利。

| 需要解决的根本问题（观察视角，非新模块） | 已有研究如何承接 |
| --- | --- |
| 意图智能：理解、发展和澄清人的目标 | P1–P8 的问题入口、意图发展、目标演化；不擅自把探索变成已确认任务 |
| 专业认知：怎样理解行业及未知机制 | 跨学科基础、专家问题表征、知识生命周期、专业原始来源与竞争解释 |
| 能力获取：缺什么、如何发现和核验 | 信息侦察、成熟产品与外部技能研究、来源审查、适用性判断 |
| 组织智能：怎样使互补能力共同解决问题 | 本次[开放专家框架](../knowledge/foundations/cross-disciplinary-foundations.md#2026-11-25开放专家框架与逐项研究)，按需求研究专家而非先绑定技能；独立分析、证据裁决、协作成本 |
| 实践与进化：怎样从判断形成实际结果 | 原有授权、实施、验证、失败归因、经验继承与下一项工作 |

这五个观察视角不是 P1–P8 的替代分类、五个必经阶段或五个固定 Agent。与本文原有 A–K 层互补：组织智能尤其连接 D/E/F 的学习、发现、选择与组合，并通过 G/H/I 的实际行动、领域应用及验收、J 的反馈修订产生价值；K 的人类授权始终有效。组织智能并不要求每次使用团队，也不意味着需要新增多智能体运行平台。

**研究边界。** 专家真实工作、知识需求、判断方法、技能和工具均是逐项开放研究对象；通过多轮外部搜索、实际案例和共同评审逐渐确认，不能将之前候选资源表当作默认配置。用户可参与任何外部研究、提出资源与质疑；AI 自主承担专业研究、比较、求证及普通授权内工作。具体长期技能绑定须共同确认，外部安装、付费、资金及其他高风险操作另行授权。研究中发现更合适的角色结构时允许拆分、合并或取消；没有证据的部分留空。

**领域关系与价值检验。** Blix/MEME 是金融链上业务的实践场，Gendan 是跟随性专项场景，信息侦察是通用产品入口；未来其他现实领域按需求出现，不预设统一产品形态。领域事实和数据以各项目实际证据为准，不将行业假设升格为 ai-d 通用真理。优先用真实任务比较直接模型、按需知识技能与真实协同方式的判断/成果增量、关键错误、用户干预、费用、维护成本；现有单模型足够就不扩建团队。验证方案沿用 [现有评测](../evaluation/first-cross-domain-tests.md)，没有独立运行证据不宣称团队已实现或有效。

**状态：USER_CONFIRMED_DIRECTION / OPEN_FRAMEWORK / EFFECT_NOT_VERIFIED。** 本节仅统一已有项目认识及研究方向，未指定专家完整需求或选定技能，未证明通用系统已运行。之后的新增知识按其实际用途归入现有入口，避免每次认识变化另建架构或重复文档。

## 2026-11-25｜认知分工与选择性外显：内部质量、外部价值、可审查性

**用户确认的原则；具体实现为可逆候选，实际增益待验证。** 复用第18节极简交互、既有 P1/P5/P6/P7/P8、[意图委托研究](2026-11-07-short-intent-goal-context-delegation.md)和[现有评测](../evaluation/first-cross-domain-tests.md)，不新增认知层、固定专家、技能绑定或强制流程。AI 承担专业分析、证据核对、反证、质量修正和常规协调，不把中间工作转嫁给用户；人保留目标、价值取舍、关键授权、参与学习和质疑的权利。内部化不等于降低实际检查，也不要求记录或公开模型私有推理。

**判断依据（按需使用，非逐项强制表单）：** 信息是否改变目标、判断、行动、风险、资源、授权或验收？是否只有人能决定或提供？延迟反馈是否造成损失？用户此刻是在委托交付、共同研究还是学习？依情境选择：常规内部消化；必要结果与简要依据默认呈现；详细可核验依据/来源/测试或交付物按需展开；重要未解决风险、关键证据缺口、目标冲突、失败及重要假设主动反馈；重大不可逆行动、超出授权、正式长期技能绑定等先取得适当授权。若无法继续，交付已验证的部分并说明真实阻塞，不用漂亮总结掩盖失败。常规修正不逐项打扰，但实质改动、验证覆盖及剩余限制在交付时说明。普通任务直接做，不强制五层输出。

**冲突裁决：** 自治不等于代替价值决定；少打扰不等于隐藏坏消息；默认简明不等于强制简短（教学、共同研究或复杂决策可以深入）；专家意见不是独立证据，未运行独立子代理就说明单模型多视角，不伪造协作或审查。用户共同研究权、既有安全授权及开放技能逐项求证继续有效。证据来源、关键假设、行动与验证结果是可审查工作记录，和原始模型思考不是同一事物。仅使用实际可用的工具与日志，不假称后台状态或完整内部记录。

**外部方法支持（设计借鉴，不证明本项目效果）：** Horvitz 的[混合主动交互](https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/)强调不确定性及主动交互的成本收益；Amershi 等的[人机交互准则](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)支持情境相关信息、纠正及可获取的行为解释；[NIST AI RMF 1.0](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)将潜在/实际不利后果通知与透明性关联。由此提出上述按任务和风险分配反馈的候选，不照搬为新审批平台。

**应用与停止：** 项目诊断先自行定位复现问题，向人提供结论、证据、实际修复与限制；市场研究内部过滤噪音，但证据冲突、未知、执行能力或重大风险须呈现，不因简洁放宽权限；信息侦察仅推送足以改变判断的发现并附来源，未发现不代表外部不存在；用户要求共同学习时保留必要专业解释与研究入口。先复用现有协同技能与跨领域评测，若实际出现持续漏报/重复打扰再考虑工程化。状态：已形成原则与桌面场景检查，尚无独立模型对照、宿主运行时接入或实际收益证据。
