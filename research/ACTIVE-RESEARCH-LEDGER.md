## 2026-11-14｜K-A06：纠偏方法的第二次源码实证——纠正钱包采集的错误覆盖判定

**触发与正确基线**：用户同意从概念研究进入“主动发现、正确定位、独立验证”的实际试点；维持新确认的“上游源问题修上游，不让AI工作台重新采集”。在Blix原版钱包采集层server/wallets.js::pageSignatures中，若增量扫描没有旧签名锚点(lastSig=null)，原实现初始reached=true；即使RPC每页满额、达到pages上限并未见到历史终止边界，仍返回reached=true。这是可由源码逻辑证明的**错误覆盖状态**，不需要声称主网已经发生丢交易事故。

**实际修复**：在既有wallets.js将reached初始化为Boolean(first)而非first||!lastSig；没有上次锚点的增量扫描必须通过真实短页或识别旧锚点才能判已到达边界。原函数下游checkpointWalletPage继续沿既有钱包签名作业、水位与风险记账，不创建第二套采集源；未验证状态用“older events may be missing”替代“the oldest were skipped”的过度断言。

**反例与对照**：test/wallet-evidence-chain.test.mjs新增纯离线模拟：无lastSig、连续两页各50签名、刚好达到页上限，必须reached=false；短页返回true；已有lastSig短页场景不应回归。这是可复现的本地算法边界测试，并非模拟真实第三方供应商全部行为。相关源码：[wallets.js](https://github.com/sunshihao001/grok/blob/integration/blix-evidence-readonly-20261108/server/wallets.js)、[wallet-evidence-chain.test.mjs](https://github.com/sunshihao001/grok/blob/integration/blix-evidence-readonly-20261108/test/wallet-evidence-chain.test.mjs)。

**跨层关系**：目标O2/O3/O4、来源采集S4、事实覆盖契约S5、反例S6、纠偏S7；纠错发生在已有数据源接入所有者，而非AI sidecar或提示词。纠偏范围只限“历史覆盖状态”，不扩大成“全市场实际漏报已证实”，也不能将满页视作一定漏包。

**状态与下一步**：已提交源码修复与回归测试；GitHub Actions最终验收按最后提交SHA核查。真实供应商签名补查/数据覆盖质量与完整Mint链仍UNKNOWN。若CI成功，可把此例视为SOURCE_CODE_FIXED + OFFLINE_REGRESSION_PASSED，**不能称REAL_MARKET_COVERAGE_VERIFIED**。下一步优先用有界真实RPC证据验证补查和旧历史窗的风险，但不重复造数据源系统。

## 当前目标锚点

**用户自然语言 → AI 识别深层意图与错误前提 → AI 形成适当的专业问题表征与研究/实施任务 → 从成熟专业知识和现有产品中选择方法 → 授权内执行并核验成果 → 保留依据、错误、待修订项与下一步候选 → 由新证据和用户反馈继续修正。**

此处是研究与协作能力的关系，不是所有任务必须遵循的流水线。短问题可直接回答；需要调查的深入；风险高的先核授权。**AI 不得因为上一次主动选定某个具体案例，就宣称用户的长期目标已经改变。**

### “专业化表达”具体指什么

- **把目标说准**：用户到底想获得什么结果，已有目标是否被替换？把确认目标与 AI 猜测分开。
- **把问题找全但不滥列**：找到真正影响结果的专业机制、隐含条件、竞争解释和未知；可能来自用户未提过的学科。
- **把工作说成可执行任务**：明确要参考哪些已存在的资料/成熟成品、研究深度为何、交付物如何检查、何时继续或停止。
- **允许研究重构问题**：新证据可以改变研究假设和优先级，重大个人目标仍由用户决定。
- **将修改与下一步衔接**：不能只写“下轮继续”；要记录上一轮尚未解决的具体理由以及下一步要取得的证据。

例如用户只说“按照建设来，继续”：AI 可以恢复当前目标与最新记录，判断哪项结论已核实、哪项只是推论，选择最有信息价值的未解问题，把它展开成一段**给 AI 自己使用**的专业任务说明，再执行。无需反问用户先列专家名单或写五百字提示词。

## 研究风险锚点｜继续课题之前先判断方向还是方法失效

**何时适用**：准备选择下一轮的复杂研究/持续建设方向、已经多轮没有可观察的新成果、或者用户反馈“太浅/还在原地打转”时，AI 才重点进行这项判断。普通问答不需要额外反思表。**不把前一轮 AI 自己提出的下一步视为当然正确。**

| 风险类型 | 应看的实质证据 | 合适的动作（按情况择一） |
| --- | --- | --- |
| 课题价值不足 | 即使取得预期结论，也无法影响人类目标、重要知识缺口、现实判断或授权内交付；已有成熟成果足够解决而仍在重造 | 暂停或降级、保留资料与重启条件 |
| **课题有价值，但方法无效** | 同一类型资料/模型推论反复出现；新术语不提供新机制；只写下一轮研究计划却未改变知识或选择；关键研究对象始终没被核实 | **不否定课题**，改用源级调查、独立对照、专业实证、成熟成品复用或实际验证等更适用的办法 |
| 方法可行，但执行和证据受阻 | 需要的数据、工具、授权或外部反馈未到位；错误把模拟/静态源码当实跑，或无法复查结论 | 写明具体阻塞，转能完成的低风险成果；无法获得证据时暂停，保留 UNKNOWN |
| 继续有价值，但当前优先级下降 | 新研究、新实际需求或风险改变了优先级；旧方案仍有知识价值 | 保留历史与重启条件，把资源转向价值更高的工作 |

**风险信号不等于自动停止条件**。长时间研究一个复杂而重要的问题可能完全合理；要看**信息增量、解释增量、可检验性、决策/成果变化及成本**，不是机械计数轮次、字数、论文、专家、提交。亦不能用“每次都换一个新课题”冒充主动探索。

**研究前真正的自我审查**：当前工作的意义是什么？相比上一轮究竟增加了哪些能被指出的事实、机制、证据或成果？如果没有，是方向本身不值得做，还是研究方法/资料/任务定义有误，还是仅被现实限制阻塞？下一项取证或行动能否改变判断？有更好的路线吗？

**研究选择的实际表达可以很简短**：例如“这个方向仍重要；但继续搜同类澄清论文已收益很低，本轮改为对照真实任务并测量用户纠错次数”。仅在其确实改变下一轮研究方向/方法时记入台账，不需要每次输出完整表格。AI 必须在授权边界内行动，不能因评估认为有价值便自动实施不可逆/对外操作。

### 当前课题的一次具体风险判断（2026-11-08）

**课题**：“普通人的口语化表达如何由 AI 转成准确的专业问题/行动，并跨轮保持研究质量？”对 ai-d 原始目标直接相关，且 AskBench / VagueBench / 长程 Agent 失配研究说明现实问题确实存在，**价值判定：保留**。

**研究方式的已知问题**：仓库已有多份专业问题表征、主动澄清、搜索、停止与跨学科研究文档；[既有评测](../evaluation/first-cross-domain-tests.md)多次登记独立模型对照 NOT_RUN。新报告不断增加，但效果证据没有同步累积。**风险判定：方向有价值，继续扩写类似理论/计划的边际价值较低；不宜以再写一份方案作为主要成果**。

**当前建议的改变**：先复用已有评测设计与成熟基准，对未泄漏的完整任务进行原句与 AI 专业任务表述的可复查比较；检验是否减少重要遗漏、错误假设、用户纠错负担与失败成本。若缺独立模型或专家判据，可先形成真实来源支撑的任务/评审材料，但必须如实标明未运行；不能因缺完美测量而停止全部低风险实际工作。此建议尚非已执行/已通过实验的结论。

**跨项目风险判断的已知参照（未进行本轮工程实测）：** Blix B02/B03：当前真实业务目标是“Mint→钱包买入→Token接收→卖出→跨Mint资金候选”，而 B02 的已读标记/失败重试、B03 的签名覆盖水位会直接影响整条链事实能否查全。因此**方向仍有价值**，但继续堆理论、报告或候选关系图则**方法不对**；应该使用真实代码中的故障注入、确定性重放与已存在的分页组件形成小范围、可执行的反例。若恢复链路不能降低漏记/错误声明覆盖的风险，或发现原有实现已在别处可靠处理，就修正优先级而非继续扩建。

### 第一轮跨项目实际检验（2026-11-08）

将此风险锚点应用到 Blix 的B02/B03：原课题“交易证据连续性”对完整业务链有高价值，但反复写架构说明无法解决。于是把**研究方式从源码静态推演改成故障注入与恢复验收**。独立的 [Blix PR #18](https://github.com/sunshihao001/grok/pull/18) 新增持久处理状态、缓存RPC重放、有限重试候选；GitHub Actions已运行**19项相关新增测试全部通过**。这是一项可核查的工程成果与方法转变，**不是研究价值判断规则本身已通过独立A/B测试**。剩余的B03“完全未被发现的历史签名”不能由B02的测试覆盖，已明确保留为下一项关键未知。主产品全局CI仍有8项旧失败，未合并上线。

**方法修订的事实依据**：从“再研究如何续传”转为“保存成功、钩子失败、任务重试、同签名多钱包和超过重试上限”的确定性反例；若下轮B03仍只有新文档没有覆盖水位或有效成品比较，按风险锚点改研究方法而非继续写同义结论。

## 2026-11-15｜K-A07：从“Agent 内核”假设转向“能力整合”假设

**触发**：连续研究 Hermes、Skills、MCP、Agent Runtime、Memory、研究 Agent 后，用户进一步明确：真正可能脱颖的不是再发明一个组件，而是自己的**整合能力**。这不是用户不懂代码所以降低目标，而是对现有生态成熟度重新判断后的产品方向假设。

**本轮外部研究**：Hermes v0.23.1 及当前文档显示其已经提供大量 Runtime、Tools、Skills、Memory、Session Search、Delegation、MCP、Plugins、Cron、Gateway 等能力；2026 Agent 综述显示工具、记忆、规划、编排已成为常见基础组成；2026 memory 研究进一步把重点推向更新、失效、遗忘、治理与长期一致性。结论：继续堆 Skill/Tool/Memory 不足以形成可靠差异化。详见 [能力整合与 Hermes 演化研究](2026-11-15-capability-integration-and-hermes-evolution.md)。

**新研究假设**：ai-d 更值得研究的是 Goal-to-Capability Integration Layer：从人的真实目标出发，形成问题表征，判断能力缺口，发现可用能力提供者，按当前条件选择/组合模型、Agent、Skill、MCP、专业方法、数据与成熟项目，执行后用证据验证，再决定修订、替换、淘汰或沉淀组合经验。Adaptive Judgment / Epistemic Control 保留为其中的判断机制，不再提前宣布为最终产品内核。

**与既有知识的关系**：不新增 P9、不新增强制阶段、不推翻 P1–P8、九阶段生命周期或跨层锚点。已有意图理解→专业问题、研究风险、证据状态、纠偏、跨层追溯分别成为整合层的入口、判断、证据、修订和关系支撑；Hermes 暂时是 Runtime provider，Skills 是 procedural capability，MCP 是 tool connectivity，成熟 GitHub 项目是 capability source。

**最重要的边界**：尚未证明能力整合比普通 Agent workflow 更好；尚未证明需要改 Hermes 源码；尚未证明 Capability Graph 或专门软件必要；也不能宣称这是市场独有创新。当前状态：**SOURCE_RESEARCHED + DESIGN_SYNTHESIS / CURRENT HYPOTHESIS / NOT_MODEL_VERIFIED**。

**下一轮高价值工作**：不要再写同义理论。对 Hermes、DeepAgents、Open Deep Research、GPT Researcher、OpenWiki/Co-STORM 等逐项检查它们已经解决哪些能力选择/组合/验证问题，再选一个与 Solana 不同的完整现实任务，比较普通 Agent workflow 与动态能力整合是否减少用户纠错、无关工具调用、关键未知遗漏和失败成本。如果没有稳定收益，应停止扩大该方向。


## 2026-11-15｜K-A08：从“核心思想”进入“复杂全域系统”

**触发**：用户进一步明确：最近几轮得到的是思想层认识，但真正的 ai-d 是一个复杂的全方面、多领域项目；不能因为“能力整合”解释力强，就把整个项目压缩成一个中间层。

**本轮新增收束**：新增 [从“思想”到“复杂全域系统” V1.0](2026-11-15-from-idea-to-open-adaptive-system.md)，将系统暂时拆为 Human/Goal、Problem Formation、Epistemic/Evidence、Knowledge Learning、Capability Discovery、Capability Selection/Composition、Runtime/Execution、Domain/Project、Verification/Evaluation、Learning/Experience、Governance/Human Authority 等相互关联的层。它们不是固定执行阶段，而是需要共同解决的问题空间。

**关键认识**：
- “不会就学习优秀知识”是总思想，但 Learning 本身需要判断：查事实、学概念、找成熟实现、找真实证据、做实验、停止研究或交还用户，不能一律继续搜索。
- “能力整合”只是从目标到执行之间的核心机制之一；它必须与目标理解、知识学习、证据、验证和经验学习形成闭环。
- 多领域迁移必须区分通用方法与领域事实/方法/能力，Blix 可以作为复杂现实试验场，但不能单独证明通用性。
- 长期资产不应只是知识文档，而应逐步形成能力资产、组合/决策经验和经过验证的评测经验。
- 不能先把完整架构设计完；应由真实任务暴露缺口，再决定哪些需要程序化、哪些 Runtime 已经解决、哪些只是我们想复杂了。

**状态**：DESIGN_SYNTHESIS / CURRENT HYPOTHESIS / NOT_IMPLEMENTED_AS_A_WHOLE。保存新文件不代表系统已经实现，也不代表模型已经自动学会。

**下一步**：选择一个完整、真实、可验收、且不同于 Solana 的任务，实际测试“普通人一句话 → 自己发现不知道什么 → 找优秀知识 → 找已有能力 → 组织能力 → 执行 → 验证 → 修正”。逐项记录缺口属于模型、知识、能力发现、组合、Runtime、验证、经验还是人类授权；不先开发完整 ai-d。


## 2026-11-15｜K-A09：整合层收束为“内部机制”，验证/停止/追溯前置

**触发**：用户进一步明确：如果整合层服务普通人，普通人不应该理解或操作能力地图、Skill、MCP、Runtime 等中间层；人只需要通过聊天窗口用自然语言表达目标。与此同时，真实 Agent 使用经验显示“做错不知道停、状态丢失、无法追溯、擅自改变目标”比能力数量不足更基础。

**本轮纠偏**：
- 用户界面目标固定为“人只跟聊天窗口说话，其余全部是系统内部机制”。
- 暂不优先建设能力地图 UI / Capability Graph UI。
- 优先把“自然语言目标 → 系统组织已有能力 → 完成或明确停下来”的最小闭环跑通。
- 强制加入两个第一阶段行为：**不确定就停**、**可追溯**。
- 同时加入 **不自造目标** 作为硬约束：系统可以发现子问题和提出建议，但不能无依据把自己的偏好、方便或假设升级成用户新目标。
- 其余整合层设计从真实运行缺口中长出来，不预先完成全套架构。

**第一阶段验收指标**：Goal Fidelity、Uncertainty Stop、Stop Explanation、Traceability、Recovery、State Continuity、Evidence Boundary、User Burden。它们是当前行为验收指标，不是永久固定框架。

**知识收拢**：暂时将全域知识/系统问题导航为六个主域：
1. Human & Goal
2. Knowledge & Epistemics
3. Capability & Method
4. Runtime & Execution
5. Domain & Reality
6. Verification & Evolution

六域是导航与收拢方式，不是六步工作流；不新增 P9，不推翻 P1–P8、知识九阶段或跨层锚点。

**开发纪律**：真实任务闭环 → 验证 → 停止 → 追溯 → 失败定位 → 修正 → 观察新的缺口 → 再决定是否需要新的整合机制。暂不因理论完整性提前开发大而全的能力地图、Graph、巨型 Workflow、Hermes 核心改造或自动学习系统。

**状态**：DESIGN_CORRECTION / HIGH_PRIORITY / NOT_IMPLEMENTED_AS_A_WHOLE。


## 2026-11-15｜K-A10：Hermes 深度能力账本——先掌握 Runtime，再决定 ai-d 如何承接

**触发**：用户明确要求先把 Hermes 内部各方面能力研究、理解其实际使用方式，再结合最新 ai-d 认知决定如何做 Hermes；不能先把 ai-d 设计强行套进 Hermes。

**本轮外部核查**：截至 2026-11-15，Hermes 最新稳定 release 为 v0.23.1（2026-11-09）；v0.23.0 已将 Gateway/Session、Desktop/Webapp、Plugins、Delegation、Memory、长期运行能力进一步整合。当前官方文档与 main 源码还包含可能领先稳定版的内容，因此本轮明确区分 STABLE 与 MAIN/DOC-LATEST。主要核查了官方 Tools/Tool Search/Skills/Memory/Context/MCP/Plugins/Hooks/Delegation/Cron/Security、架构源码与 release notes。

**已形成的 Hermes 能力账本**：Model/Provider/Auxiliary Model；Built-in Tools/Toolsets；Tool Search/Progressive Disclosure；Skills；Memory/Session Search；Context Files；MCP；Plugins/Hooks；Delegation/Subagents；execute_code；Gateway/Sessions；Cron；Security/Approval。逐项记录了原生职责、实际使用边界以及与 ai-d 六域的映射，详见 [Hermes 深度能力账本](2026-11-15-hermes-deep-capability-ledger.md)。

**最重要的新收束**：
- Hermes 已经覆盖大量执行层能力，因此 ai-d 不应重新造 Tool/MCP/Skill/Memory/Delegation/Gateway/Cron 等基础设施。
- Hermes Tool Search 解决的是“已有工具太多，如何渐进发现”；ai-d 仍要研究更上层的“目标需要什么能力”。二者不能混为一谈。
- Skill 更接近 procedural memory；Memory 更适合少量稳定事实和按需历史召回；Context Files 是局部项目规则。三者都不能替代 ai-d 的知识适用性、证据和废弃治理。
- Plugin/Hooks 已提供 pre_tool_call、pre_llm_call、pre_verify、session/API/subagent 生命周期等扩展点，因此未来 Traceability / Verification / Goal/Evidence context injection 可能优先通过插件/Hook 验证，而不是修改 Hermes core；这是候选方案，尚未实跑证明。
- Gateway/Session 已成为长期运行和状态连续性的基础，不应再造第二套 Runtime，除非真实任务证明现有能力不足。
- Security/Approval 应视为 Runtime 执行前提，并与未来“不确定就停、不可逆操作需要人工授权”衔接。

**当前 ai-d 映射假设**：
> ai-d 负责 Human/Goal、Problem、Epistemic/Evidence、Knowledge Learning、Capability Gap/Selection/Composition、Verification/Evolution 的判断与协调；Hermes 负责 Runtime/Execution。

该假设尚未被真实跨领域任务验证，不能当成最终架构。

**当前尚未证明**：Hermes 在真实复杂任务中的 Goal Fidelity、Uncertainty Stop、Traceability、Recovery 是否足够；Memory/Skill 是否带来长期净增益；ai-d 最终应采用 Plugin、外部协调层、MCP、混合还是其它承载方式；是否需要修改 Hermes core。

**研究方式修订**：不再继续扩充 Hermes 功能清单。下一轮直接选一个与 Solana 明显不同、可验收的真实任务，实际运行 Hermes；记录用户原话→实际目标→能力选择→证据→验证→停止/修正→最终结果，并定位缺口属于模型、知识、能力选择、Runtime、验证还是人类授权。只有真实缺口出现后才决定 ai-d/Hermes 的新增机制。

**状态**：SOURCE_RESEARCHED + CAPABILITY_LEDGER_COMPLETED + MAPPING_HYPOTHESIS / RUNTIME_VALIDATION_PENDING。


## 2026-11-16｜K-A11：外部智能吸收层——从“保存知识”转向“吸收可验证能力”

**触发**：用户明确要求先建设真正值得关注的知识、项目和方法，为后续使用昂贵 AI 打基础；同时要求把新知识与旧知识结合，并清理已经造成污染的旧方向。

**本轮收束**：新增 [外部智能吸收层](2026-11-16-external-intelligence-layer.md)。它不是新的知识库、固定阶段或 Agent，而是跨 K2–K9 的能力视图：

> 外部世界 → 研究 → 证据判断 → 方法/模式 → 能力资产 → 项目应用 → 真实验证 → 修订/淘汰。

**与已有知识的合并**：
- K1–K9 保留，外部智能吸收层不新增 K10；
- P1–P8 继续作为问题入口，不再扩展新的问题编号；
- 跨层锚点继续负责目标、知识、数据、工程、测试和运行之间的可核查关系；
- 六域继续作为导航，不作为工作流；
- Hermes 深度能力账本继续作为 Runtime 事实来源；ai-d 不重复建设 Hermes 已有的 Tool/MCP/Skill/Memory/Delegation/Gateway/Cron 等基础设施；
- 纠偏、风险判断、证据状态和“不确定就停”继续保留，并作为外部知识吸收后的验证/淘汰条件。

**本轮明确清理的污染倾向**：
- 不再把“大而全知识库”视为 ai-d 的主要终点；
- 不再因为遗漏就不断新增阶段、专家、层级或系统；
- 不再把外部资料全文搬进长期上下文；
- 不再把 Capability Graph / Knowledge Graph / 大型 Workflow 视为当前必做；
- 不再把 Skill/Memory/MCP 当成 ai-d 必须重新实现的底座；
- 不再用文件数量、研究轮数、来源数量或模型自评证明能力提升；
- 不再把一次成功案例、单篇帖子、README 或理论类比直接升级为长期规则；
- 已出现的历史设计如果只是旧方案而没有当前证据支持，不再作为默认指令继续传播。

**一个重要修订**：过去的“知识分类、知识生命周期、知识内核”材料不全部删除。能够提供来源、机制、反例或历史决策价值的保留；已经只是重复描述、没有独立机制/证据/用途的内容应在后续清理中删除或合并。删除的对象是**污染性结论和无效重复**，不是为了追求“文件更少”而删除证据。

**当前状态**：SOURCE/DESIGN INTEGRATED；POLLUTION DIRECTIONS DEPRECATED；NOT_YET_RUNTIME_VALIDATED。

**下一步**：不再继续写同义的外部知识框架。选一个真实 ai-d / Hermes / Muse 任务，实际执行一次“发现缺口→外部研究→成熟项目/方法→能力提炼→应用→验证→保留/淘汰”，用结果判断该结构是否真的减少成本、重复开发或用户纠错。
