# ai-d 的四类目标：多视角方案比较与当前裁决


> **2026-11-07 全局复审注**：本文件仅记录 **11 月 5 日研究范围内** A/B/C/D 方案的当时比较，不代表用户后来确认整个 AI 项目必须以 B（通用认知方法评测中心）为唯一主体。进一步恢复的七八月目标还包括不同人的专业能力与思维方法、信息与现实机会发现、个人学习及真实工作/价值创造；AI 也不应因最近研究 Hermes、Skills 或工作流就自动把它作为下一轮主线。当前较完整的[全局审查及第十二节成熟机制对照](../research/2026-11-07-independent-whole-project-direction-audit.md)为**可质疑的增量证据**，不构成新的强制规则。保留本文件历史裁决，以便回溯其成立条件和不足。日期：2026-11-05｜状态：可复议的研究建议；不修改 README 中的用户确认定位。

## A｜知识参考库
**目标**：保存人机协调、目标推理、专业认知、Agent 实践、原始论文、反例。
**优势**：简单、易审阅、跨模型、公开资料引用方便。
**失败方式**：只会越积越多，无法解释何时用、如何改变行动；用户此前已出现过此类负担。
**适用条件**：研究与知识来源尚不完整，需先保证资料可追溯。
**裁决**：基础功能必须有，但不是最终价值定义。

## B｜通用认知方法的适用与评测中心（首选）
**目标**：从 A 中选择有证据的方法，测试不同任务如何调用、何时失效、什么新知识真正改变决策。
**优势**：从“保存内容”走向“在真实任务里有用”，最符合旧知识保留但避免过度约束的要求；可接不同模型。
**失败方式**：自评偏差、只挑熟悉案例、额外检索成本大于收益。
**成立条件**：至少两个异质任务、原始任务一致、检索资料可比、参考事实可查、输出判断有可核查变化。
**裁决**：**当前优先路线：A 作为材料基础，B 作为专业能力建设的主线**。

## C｜可插拔 Skill / MCP 知识适配层
**目标**：使未来 Grok / GPT / IDE Agent 或其他工作流按需使用经验证方法。
**优势**：交付接口清楚；可将专业能力嵌入现有运行时。
**失败方式**：提示词封装导致跨任务过拟合、接口维护、错误知识被强制加载。
**成立条件**：B 证明具体知识确有迁移增益，且至少两个消费者有明确的相同调用需求。
**裁决**：保留为条件性路线，不预先建一堆 Skill。

## D｜人机协调操作系统 / 自主 Agent 平台
**目标**：用统一产品运行意图理解、记忆、规划、工具、调度、权限、评价、目标更新。
**优势**：可承载长期无人值守任务和完整 UI。
**失败方式**：重造 OpenAI Agents SDK/LangGraph/MCP/A2A 已成熟的组件，增长复杂度压制研究质量；潜在目标漂移和授权失效。
**成立条件**：现有 GPT + GitHub + 成熟 SDK 无法满足被验证的实际长任务需求；预计收益明显大于搭建与维护成本。
**裁决**：暂不作为当前开发目标；真正出现缺口时应先复用成熟 runtime。

## 五种视角重新评判
| 视角 | 最优先的事 | 反例或风险 |
|---|---|---|
| 人的长期目的 | 允许目标演化，人保留重大决定 | AI 自己不断扩大目标导致偏离 |
| 专业研究者 | 从原始证据生成有条件、可反证的新认识 | 只增加概念与引用，未改变结论 |
| 产品负责人 | 找到可检查的交付与用户收益 | 构建没有用户验证的“总架构” |
| 工程负责人 | 用成熟协议与 SDK 解决执行基础设施 | 重造状态和工具层 |
| 质量评测者 | 比较基础模型与选择性知识调用 | 同一 AI 自评、过拟合和假对照 |

## 何时推翻当前建议
- B 在独立任务中稳定增加错误、成本、用户负担，且无可靠增益：退回 A 并修订知识触发条件。
- C 的两个真实工作流需要共用相同规范且有明显维护收益：优先做有限 Skill/MCP 适配。
- D 所需长时状态、审批和持续执行能力无法通过成熟框架满足，且已有实际业务收益证据：再评估独立平台。

**当前决议**：研究型通用内核，不等于统一软件中枢；主攻“目标变化＋证据适用＋下一动作价值＋可验证迁移”，保留未来基于用户选择改变方向的权力。

## 2026-11-10｜GitHub 成熟成品反向对照：从初步知识项目到高级人机协作（L0–L6）

> **注意两种“等级”不同**：用户预想的能力目标属于 L5–L6 的高级方向，当前 ai-d 的**已证明实现成熟度**远没有达到 L5。L0–L6 是需求和验收等级，不是强制阶段或新七层架构。现有 A/B/C/D 是实现路线选择，继续保留，两套不要混为一谈。

### 核心目标

让不懂行业、技术与产品的人，仅用普通话提出目标，通过 AI 的主动专业问题发现、专家知识选择、成熟成品复用、深入研究、授权内执行与可独立评价的结果，**在特定真实任务上获得接近或超过专业 AI 使用者的工作质量**；重点不是 AI 模拟朋友感情，而是像可信赖的长期高级协作者，知道历史、会发现遗漏、敢于纠错、能动手且对真实结果负责。

### 能力等级与可检查达成标准

| 等级 | 意味着什么 | 一项实际可检查成果 | 不能冒充的情况 |
| --- | --- | --- | --- |
| L0 基础问答 | 回答明确问题 | 基础事实准确 | 答得长就算专业 |
| L1 意图理解 | 恢复不完整目标、正确选择该问/该查的未知 | 一个模糊要求被转成正确目标，减少不必要追问 | AI 自己擅自改变人生/项目目的 |
| L2 专业发现 | 从普通话发现相关行业术语、专家关注线索、隐藏变量和竞争解释 | 在用户未提示专词的题目上提出至少一个可核查的新关键问题并找到原始证据 | 角色名称堆砌/术语数量 |
| L3 深度共研 | 跨来源、跨专业取证、产生可反证的新认识并准确讲清 | 同一任务相比原答新增受来源支持的判断，且能说明失败条件 | 搜索/文档数增加 |
| L4 专业执行 | 将研究转换成软件、数据、配置、验证与实际交付 | 用成熟工具完成授权任务并回读、运行/检查结果 | 写方案或模拟即宣称真实交付 |
| L5 长期主动伙伴 | 持久恢复目标、在有价值的时候提醒或主动推进、避免打扰及越权 | 多轮跨会话项目中恢复变更，及时发现依赖并正确执行/请求授权 | 只有 cron 或记忆就称自主伙伴 |
| L6 经基准验证的认知增强 | 非专业用户借 AI 在限定真实任务上达到/超过专业 AI 使用者，能持续复现 | 固定工具/资料/预算下独立任务与专业人士基线对照，质量、正确率、成本及用户负担多维成立 | 自评、选出的成功个案、营销收益 |

**当前诚实定位**：ai-d 有 L1–L3 的方法研究和少量真实源码反例；L4 有在业务项目中的局部交付，但没有归因到 ai-d 的独立效果；L5、L6 尚未由本项目验证。不要因文件写出 L6 就宣称完成。

### 成熟开源成品：它们已经解决什么、没有解决什么

| 项目（GitHub 已核对 README/目录） | 可直接借鉴的成熟能力 | 对 ai-d 的边界与判断 |
| --- | --- | --- |
| [Hermes Agent](https://github.com/NousResearch/hermes-agent) | 多渠道助理、跨轮记忆、对话搜索、经验形成 Skill、调度、并行委托 | 提供长时执行/经验组织参照；README 的 self-improving 是作者能力主张，尚不证明在专业未知发现中比 GPT 更强 |
| [Letta Code](https://github.com/letta-ai/letta-code) | 状态化 Agent、记忆重写、Skill、消息搜索、跨渠道、子 Agent、权限、定时任务；现行实现已从 letta-ai/letta 移往 letta-code | 长期状态与可修订记忆有用；自修改记忆存在污染风险，需保留来源、撤销/反例及目标版本 |
| [OpenClaw](https://github.com/openclaw/openclaw) | 个人 AI 的跨消息渠道与设备工具协调、Gateway/权限等 | 若出现跨渠道行动需求可评估整用；不是先安装才可以提高研究质量，需安全审计 |
| [STORM / Co-STORM](https://github.com/stanford-oval/storm) | 多视角问题提问、资料综合、人和 AI 共同知识探索；已核对 collaborative_storm 代码目录 | 最接近“从一个小问题发现其他专家问题”的研究部件；其文章生成不能自动代表专业决策或产品成果 |
| [Open Deep Research](https://github.com/langchain-ai/open_deep_research) | 可配置深度检索与多来源研究；已核对 deep_researcher、prompts、state 代码入口 | 适合补研究广度、深度与证据覆盖；搜索多不等于抓到真正的隐藏因果机制 |
| [Deep Agents](https://github.com/langchain-ai/deepagents) | 子代理隔离、持久上下文、文件、工具、Skill、人类审批；含 evals 目录与评测目录清单 | 可承担长程执行底座，不必自建新多 Bot 系统；运行状态与领域专业能力应分开评价 |
| [π-Bench](https://github.com/Simplified-Reasoning/Pi-Bench) | 100 个多轮任务、5 个专业背景、隐藏意图和连续工作产物；按主动性 PROC 与完整性 COMP 检验 | 适合借鉴 L1、L4、L5 的独立评分，不能替代本项目对专业用户的外部对照 |

来源核验说明：这一轮直接经 GitHub 读取以上仓库主页或指定目录；部分是作者功能声明，**未在 ai-d 统一安装、跑整套系统、验收跨仓集成或实际性能增益**。与 11 月 7 日已有成熟系统研究交叉时只补有改变的发现，不重复建立第二份成品索引。

### 实施优先级：先证明“更懂行”，再决定要不要做常驻代理

**近期优先 P0（L2/L3）**：用未被 AI-D 现有报告提前剧透的问题，固定用户原始短句、资料时点、工具与工作预算，对照 A 普通回答、B 按需读取 ai-d 专业判断方法、C 过量历史/固定专家负对照。核心评分是找到用户不懂但重要的专业线索、证据准确率、错误增补、任务决策变化、用户需纠正次数、成本；不让同一生成者给自己独立打分。**当前 NOT_RUN**。

**P1（L4）**：挑选 1–2 个真实合法可逆任务，将 B 路线实际交付并重开核验；包括跟单中“捆绑钱包→独立群体→接收者卖出→是否可跟”的只读调查，以及另一行业不相关任务。要求有实物/结果，不以一份总结代替。**当前本规划 NOT_RUN**。

**P2（L5）**：只有在确实出现跨会话目标丢失、忘记后续依赖、长期监控成本高等实际问题时，再比较直接用 Letta Code / Hermes / OpenClaw 或现有 ChatGPT 工具，而不是自建完整中枢。评估记忆污染、提示词注入、误报提醒、重复执行、越权与权限恢复。

**远期 P3（L6）**：在两种以上陌生领域收集独立专业人士/熟练 AI 使用者的实际任务基线，固定可访问数据、工具和资源预算，评估非专业用户+增强 AI 与专家+普通 AI 的交付质量、遗漏、时间、成本、可复现性。只有实际超过基线才写“在该任务上超过专家用户”；无普遍超越承诺。

### 最应防止的四种旧错误

1. 把“用户提出一个新要求 → 新增一条 AI 指令 → GitHub 提交成功”当作模型能力提升。
2. 把多个专家名称/专业词汇堆叠当作深度，忽略专家实际注意的线索、因果机制与可执行判断。
3. 把云端 Agent、记忆、定时器和自修改 Skill 的技术能力误当作认知质量已经提升。
4. 没有独立评测就称 AI-D 已胜过基础模型或专业人士，或因尚未 A/B 便否定来源支持的局部可用发现。

**本轮交付**：核查候选成品、分离成熟底座与独特价值、定义 L0–L6 与具体验收/优先级，更新原有决策文件。**未交付**：新 Agent 产品、运行时集成、盲测结论、专家胜负结果。下一项具体工作应直接使用已有 evaluation/first-cross-domain-tests.md，做少量新题的对照，而不是再造一个评测体系。
